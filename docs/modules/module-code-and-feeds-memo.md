# 讨论备忘：领域模块应该能自带 feed 和配套功能，安全另想办法

2026-11-11 记录。状态：使用者提出了需求，还没有决定。第 1、2 节是对照当天代码和 ADR 查证过的事实，第 3 节是使用者的原则，第 4 到 7 节是设计意见和要讨论的问题。

## 起因

做「市场信号监控与预警」（盯盘条件 tripwire，PR #71 起的一组 PR）时，使用者问：这个功能要有 us-market 模块才会打开，为什么它的代码不在模块里？

回答是：宿主不从模块加载代码，盯盘检测和行情轮询只能写在宿主的 `src/sources/market/` 里，模块只负责打开它。使用者的意见是：

> 我们不能因噎废食。大的原则上，领域模块当然应该有 feeds 的设置和相关功能的配套。模块的安全问题应该想办法 self-contain，或者有第三方的安全审计，或者 Super Agent 有基础的审计确认。要点是允许模块带功能，把安全和模块的功能解耦，而不是为了安全放弃模块的功能。

## 1. 现在模块能放什么，代码在哪里跑

一个模块是 `modules/<名字>/` 下的一个目录。宿主启动时读它，之后不再读。

| 模块里的东西 | 谁读、谁执行 | 在哪个进程 |
|---|---|---|
| `module.json`（来源、定时器、工具开关、队名） | 宿主解析 | 宿主进程 |
| `rules.md` | 宿主解析，幕僚长按规则开任务 | 宿主进程 |
| `skills/`、`agents/` | Worker 读，成员读 | Worker 子进程 |
| `prepare`（一行 shell） | 宿主在任务目录里用 `bash -lc` 跑一次，密钥类环境变量被去掉，推断任务不跑 | 单独的子进程 |
| `sources[].feed` | 宿主按 `feed.kind` 在 `FEEDS` 表里找代码 | 宿主进程，代码在 `src/sources/` |

所以「模块里没有代码」这个说法不准确。模块已经能带代码，只是这些代码不进宿主进程：

- `prepare` 是模块自带的 shell 命令，宿主会执行它。
- `skills/` 里可以放脚本，带 `bash` 的 Worker 照着技能说明去跑。
- `modules/toy-market/feed.ts` 是一个模块自带的 feed 脚本。它在宿主之外运行（`just toy-feed`），把 JSON 文件丢进宿主的收件箱，走「外部投递」这条路。

模块唯一放不进去的，是要在宿主进程里运行的代码，也就是 `feed.kind` 背后的那一段。目前登记过的只有 `massive-stocks` 一种（`src/sources/feeds.ts`）。

## 2. 当初为什么这样定（更正之前的说法）

之前回答使用者时说「原因是安全」。对照 ADR-0005 原文，这个说法不完整。ADR-0005 在「没有采用的做法」里写的是：

> 模块自带代码，宿主动态 import：模块从「数据」变成「任意代码」，宿主要定义插件接口和版本，换不来什么。

这句话里有三个理由，安全只是其中之一：

1. 安全。模块里的代码会和宿主在同一个进程里运行，能拿到宿主的一切：行情密钥、Telegram 的 bot token、`state.db`、所有任务。
2. 成本。允许模块带代码，就要定义一个插件接口，并且管理它的版本。
3. 当时没有收益。那时只有 us-market 一个真实数据源，自己写在宿主里最省事。

第 3 条现在已经变了。盯盘功能是第一个「检测逻辑明显属于某个领域」的例子。往后的邮件、RSS、日历、加密货币行情也会是这样。第 2 条的成本还在，但它是一次性的。真正要解决的只有第 1 条。

另外要说明，「模块代码不进宿主进程」并不等于「模块代码是安全的」。`prepare` 和 Worker 的 `bash` 今天就在同一个系统用户下运行，能读到 `secretsFile`。这个缺口记在 ADR-0016 里，要等 Worker 沙箱来补。所以模块安全本来就需要单独的方案，和 feed 放在哪里没有关系。

## 3. 使用者的原则

1. 领域模块应该能带上它自己的 feed，以及配套的功能：检测逻辑、`lookup` 能查的操作、像 `tripwire` 这样的写工具、预警文字。
2. 安全要和模块功能分开处理。可选的办法有三种，可以组合使用：模块自我封闭（self-contain），第三方安全审计，Super Agent 自己做基础的审计和确认。
3. 不能因为安全问题，就不让模块带功能。

## 4. 一个 feed 在宿主里会碰到什么

要让模块带 feed，先要看清 feed 今天能做哪些事。插件接口要管的就是这张表。下表按 PR #71 到 #73 落地后的 `FeedContext` 和 `Feed` 整理。

| feed 能做的事 | 今天的入口 | 风险 |
|---|---|---|
| 提交触发 | `ctx.submit` | 往内核写数据，正文会被幕僚长读到，可能带注入内容 |
| 读写自己的游标 | `ctx.readCursor`、`ctx.writeCursor` | 只影响自己 |
| 直接对使用者说一行 | `ctx.post`、`ctx.raised` | 内容会发到 Telegram，离开本机 |
| 存使用者的数据 | `ctx.readUserData`、`ctx.writeUserData` | 可能是持仓这类敏感数据 |
| 回答 Worker 的查询 | `Feed.lookup` | 返回的内容进模型上下文 |
| 让使用者改条件 | `Feed.tripwires` | 宿主先查权限，再转给 feed |
| 访问网络 | feed 自己发 HTTP 请求 | 能把数据发往任何地址 |
| 读密钥 | `marketFeed` 读 `secretsFile` | 拿到密钥就能冒用 |
| 共用请求额度 | 宿主里只有一个 `MarketClient` | 一个 feed 发太多请求，别的 feed 和 `lookup` 就要等 |
| 和宿主一起启停 | `start`、`stop`、`problem` | 代码一崩，在同一个进程里会拖垮宿主 |

前六行已经是一个窄接口，参数都由宿主校验。后四行是今天「代码写在宿主里」才拿得到的权力。把后四行收进一个声明清单，由宿主来执行，模块带代码就不再等于「任意代码」。

## 5. 可选的方向

| 方向 | 做法 | 模块能带功能吗 | 安全靠什么 | 成本 |
|---|---|---|---|---|
| A. 维持现状 | feed 代码写进宿主的 `FEEDS` 表 | 不能，要改宿主 | 代码审查 | 每种新数据源都要改宿主 |
| B. 宿主进程内加载 | 宿主 `import` 模块里的 feed 代码，配合审计或签名 | 能 | 只能靠审计，运行时挡不住 | 小，但一个坏模块就能拿到全部密钥 |
| C. 独立子进程 | 模块的 feed 在自己的子进程里运行，通过 socket 用 JSON 和宿主说话，协议就是第 4 节的前六行；网络、密钥和额度由宿主按清单发放 | 能 | 进程隔离、权限清单、宿主执行、安装时由使用者确认 | 中：一个协议，一个启动器，一份清单格式 |
| D. 声明式 feed | 在 `module.json` 里写「每隔多久请求哪个地址、取哪个字段、超过多少就触发」，不写代码，宿主内置一个通用执行器 | 能做简单的 | 没有代码要审 | 小，但只覆盖简单的轮询 |
| E. WebAssembly 沙箱 | 模块的 feed 编译成 wasm，宿主在沙箱里运行 | 能 | 沙箱本身 | 大：要写 wasm 工具链，生态也不成熟 |

我的看法是 C 为主、D 为辅：

- C 和 Worker 今天的做法一样。Worker 就是一个子进程，凭令牌经 socket 调用宿主，宿主逐个请求核对权限。feed 走同一条路，宿主里不会多出第二套机制。
- C 把「功能」和「安全」分在两处，正好符合使用者的原则。功能由模块的代码决定，安全由宿主按清单执行，审计和确认是加在清单上的额外一层。
- D 能覆盖 RSS、天气、一般 REST 接口这类「隔一段时间问一次」的数据源，连代码都不用审。
- B 只能靠事前审计，运行时什么都挡不住。E 现在太重。

us-market 可以当 C 的第一个迁移对象。盯盘的检测已经写成纯函数（`src/sources/market/tripwires.ts`），轮询和请求队列也集中在 `MarketSource` 和 `MarketClient` 里，迁出去的边界很清楚。

## 6. 安全怎么和功能分开

下面按方向 C 列出一个可能的组合，每一层都可以单独讨论。

1. 权限清单。模块在 `module.json` 里声明它的 feed 要什么：要访问哪些网址（白名单）、要哪些密钥的名字、每分钟最多发几次请求、要用第 4 节前六行里的哪几项。没有声明的，宿主一律不给。
2. 宿主执行清单。密钥由宿主在启动子进程时只传声明过的那几个。网络请求由宿主代发，或者在子进程层面限制出站地址。额度由宿主统一排队。子进程崩溃只影响这一个 feed，宿主照常运行，并把原因写进「关注的来源」。
3. 安装时由使用者确认。第一次加载一个带代码的模块，或者它的清单变了，宿主出一张卡片，列出它要的网址、密钥和权限，使用者点「允许」才启用。这和 ADR-0010「宿主出题，使用者点击才算数」是同一种做法，不靠模型判断。
4. 锁定版本。使用者确认的是某个具体版本：宿主记下代码文件的哈希，代码一变就要重新确认。
5. 审计。分三档。内置模块随仓库一起审查。第三方审计过的模块带一份审计记录或签名，宿主只做核对。没有审计的模块，宿主做一次基础检查：静态扫描代码里的网络地址、进程调用和文件访问，把结果写在确认卡片上，由使用者决定。
6. 能随时撤销。模块开关（PR #27）关掉一个模块，它的子进程就停掉，权限也一起收回。

第 1、2、3、6 层不需要任何外部服务，Super Agent 自己就能做。第 4、5 层是给开源以后、装别人写的模块时用的。

## 7. 和手上的工作是什么关系

- 盯盘这组 PR（#71 起）照现在的分层做完，不等这份备忘的结论。它新增的 `FeedContext.post`、`raised`、`readUserData`、`writeUserData` 和 `Feed.tripwires`，正好可以作为方向 C 的协议草稿。
- PR #27（模块开关、列表、新建骨架）是第 6 层的前提，已合并（cefb2c1）。
- Worker 沙箱（ADR-0016）和这里是同一类问题：在子进程里运行的代码能拿到什么。两件事最好一起设计，共用一套「子进程拿什么权限」的做法。
- 模块指南要补一节「来源的三种接法」（宿主运行的 feed、外部投递、定时器），并附一张宿主登记的 feed 清单。这一节先按现状写，以后选定方向后再改。

## 8. 待决定的问题

1. 方向选 C 加 D，还是有别的考虑？
2. 第一个迁移对象是不是 us-market？还是先用一个新的数据源（比如 RSS）试协议，us-market 暂时不动？
3. 网络限制是由宿主代发请求，还是在子进程层面限制出站？前者更严，但 feed 的写法会受限；后者要依赖操作系统的沙箱，在 macOS 上是 `sandbox-exec`。
4. 安装确认卡片要不要在 Telegram 上显示？按 ADR-0016 处理成员上限的先例，可能只在网页上显示。
5. 要不要先写一条 ADR，把「模块可以带在子进程里运行的代码」定下来，修订 ADR-0005 的那条「没有采用的做法」？
6. `prepare` 和技能里的脚本，要不要也纳入同一份权限清单？

## 下一步建议

PR #27 已合并。下一步把方向 C 的协议和清单格式写成一条 ADR 草稿，和 Worker 沙箱放在一起讨论。等 ADR 定了，用一个新的数据源做第一次试点。
