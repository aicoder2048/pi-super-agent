# 讨论备忘：领域模块架构升级

2026-11-11 记录。状态：讨论稿，没有决定。

这份备忘是后续讨论的提纲。第 1、2 节写目标和现状（现状对照当天的代码和 ADR 查证过），第 3 到 9 节是设计意见，第 10 节是建议的讨论顺序和要决定的事。

全文用一个「个人医疗健康」模块做例子，因为它几乎用到模块的每一种组成，也最能暴露隐私、权限和安全问题。

相关文档：

- `docs/modules/module-design-review.md`：2026-11-10 对模块设计的评审。
- `docs/modules/module-user-guide.md`：现在的模块使用指南。

## 1. 目标

使用者提出的要求：

1. 一次把模块的架构理清楚，之后加新领域不用再改宿主。
2. 模块真正能插拔：装上就有这个领域，拿掉就没有，最好不用重启宿主。
3. 不懂编程的使用者也能从零做出一个模块：有模板，有制作工具。
4. 模块是领域模块。一个领域需要的东西，都应该能放进同一个模块里。
5. 安全另想办法，不能为了安全放弃模块的功能（见 `module-code-and-feeds-memo.md`）。

## 2. 一个领域模块由什么组成

以个人医疗健康模块为例，使用者列出了六类组成：

| 组成 | 医疗健康模块里的例子 |
|---|---|
| 1. 领域知识 | 官方指南（如《2022 AHA/ACC/HFSA 心力衰竭管理指南》）、文章、研究论文 |
| 2. 数据 | 患者基本信息；个人医疗记录：影像检查报告、血液和尿液检验报告、出院小结、处方、诊断报告、病历 |
| 3. 领域工具 | 胰岛素敏感度计算器这类确定性的计算 |
| 4. 领域技能 | 问诊流程、复诊流程、多学科专家会诊、报告复核和审计（例如 AI 自己看影像，核对医生的结论）、关键指标（例如三种肿瘤标志物）的跟踪、趋势分析和预警 |
| 5. Feeds | Google Drive 里的体检报告、邮箱里医院发来的报告和通知、智能设备的数据（webhook 或其他投递方式）、某些药物（例如肿瘤靶向药）的前沿研发进展 |
| 6. 专家团队 | 配套的 Agent Team，每位专家有自己的分工、专业能力和技能 |

### 2.1 现在能放进模块的，和放不进的

对照现在的代码（`src/modules.ts`）和 ADR：

| 组成 | 现在的支持 | 差距 |
|---|---|---|
| 1. 领域知识 | 只有 `skills/` 下的 Markdown。助手按需读整篇文件，没有检索 | 几百页的指南和几十篇论文放不进技能文件，也没法按段落检索和引用出处 |
| 2. 数据 | 没有位置。ADR-0009 写明「模块里的数据还没有位置，等有具体数据时单独设计」。私人内容只能放在状态目录的模块文件夹里（指南 7.8 节） | 没有存放规则、没有结构、没有访问控制，也分不清「模块本身」和「某个人的数据」 |
| 3. 领域工具 | 模块只能打开宿主已有的工具（`tools: ["lookup", "tripwire"]`）。自己的计算只能写成脚本，靠带 `bash` 的 Worker 去跑 | 推断任务没有 `bash`，用不了这些脚本；脚本没有输入输出约定，也没有测试 |
| 4. 领域技能 | `skills/` 支持得最好 | 技能里要的「定期跟踪、越线预警」没有对应的机制；盯盘条件（tripwire）目前只服务行情 |
| 5. Feeds | 三种接法：宿主运行的 feed（只登记了 `massive-stocks`）、外部投递到收件箱、定时器 | 要接 Google Drive、邮箱、设备 webhook，都得改宿主；见第 6 节 |
| 6. 专家团队 | `agents/` 支持成员定义：工具、技能、模型 | 基本够用。缺的是会诊这类多位专家一起讨论的协作方式 |
| 插拔 | 宿主启动时加载全部模块，没有开关。拿掉一个模块只能删文件夹，或改 `modulesDirs`（ADR-0009）。PR #27 加了开关，已合并（cefb2c1） | 改任何模块都要重启宿主 |
| 制作 | 有一份很长的使用指南。PR #27 加了 `just module-new` 生成骨架 | 没有制作工具，没有校验和预演工具，小白做不出来 |

## 3. 模块的定义要先分清两件事

讨论之前先把一个概念分开，后面的设计都建立在它上面：

- **模块包**：可以分享的部分。知识、技能、工具代码、feed 代码、专家定义、规则、模板。同一个医疗健康模块，可以给很多人用。
- **模块实例数据**：只属于某一个使用者的部分。病历、检验报告、处方、设备数据、个人的跟踪指标和阈值、连接各个服务的授权。它永远不进模块包，也不进仓库。

今天这两件事混在一起。例如自选股写在 `module.json` 里，所以带自选股的模块不能分享。盯盘这组 PR（#71 起）已经往这个方向走了一步：使用者的盯盘条件存在 `state.db` 的 `source_user_data` 表里，不在模块文件里。

建议把这条分界写成架构的第一条规则：

1. 模块包是只读的。宿主从不往模块包里写东西。
2. 实例数据放在状态目录下，每个模块一个独立的空间，由宿主管理访问。
3. 卸载模块包时，宿主询问要不要保留实例数据。默认保留。

## 4. 建议的模块结构

下面是医疗健康模块装好以后的样子。名字都是草稿，供讨论。

```

  module.json                            清单：名字、版本、需要的宿主版本、权限、组成
  README.md                              给人看的说明
  knowledge/                             领域知识
    guidelines/2022-aha-acc-hfsa-hf.md   使用者自己导入的指南（版权见 5.1）
    sources.json                         每份知识的出处、版本、日期
  data/
    schema.json                          这个模块的数据长什么样：检验结果、影像报告、处方……
  tools/
    insulin-sensitivity/
      tool.json                          输入、输出、单位、适用范围
      index.ts                           计算代码
      cases.json                         测试用例，装模块时宿主先跑一遍
  skills/
    consult/SKILL.md                     问诊流程
    follow-up/SKILL.md                   复诊流程
    mdt/SKILL.md                         多学科会诊
    report-review/SKILL.md               报告复核和审计
    marker-tracking/SKILL.md             肿瘤标志物跟踪、趋势和预警
  feeds/
    drive-checkups.json                  声明式：用 Google Drive 连接器，看某个文件夹
    hospital-mail.json                   声明式：用邮箱连接器，按发件人过滤
    device-webhook/                      带代码的 feed，在子进程里运行
    targeted-drug-research.json          声明式：定期查论文库和临床试验库
  agents/
    cardiologist.md
    endocrinologist.md
    oncologist.md
    radiologist.md
    clinical-pharmacist.md
  rules.md                               什么情况下开任务
  evals/                                 考题：拿来验证这个模块答得对不对

~/.pi-super-agent/modules-data/personal-health/   实例数据（只属于这个使用者）
  records/                               导入的报告原件和提取出的结构化数据
```

## 5. 六类组成，各自要怎么设计

### 5.1 领域知识

**是什么。** 指南、文章、论文。特点是篇幅长、要引用出处、会出新版本。

**建议的做法：**

- 知识以文件的形式放在 `knowledge/` 下。宿主建一个按模块隔离的检索索引。
- Worker 用一个只读工具查知识，例如 `knowledge { op: "search" | "read", ... }`。返回的每一段都带出处：文件、章节、版本。这个工具和 `lookup` 一样，由模块在 `tools` 里打开。
- `sources.json` 记录每份知识的来源和日期。技能可以要求「回答时必须引用知识库里的出处」。
- 指南和论文大多有版权，模块包里只放公开可分享的内容。受版权保护的全文，由使用者自己导入实例数据，模块包里只放获取方式。

**要讨论的问题：**

- 检索用关键词，还是向量，还是两者都用？向量检索要选嵌入模型，而嵌入模型可能按量计费，选之前要先确认费用。
- 知识要不要分「权威」和「参考」两级，回答时优先引用权威的？

### 5.2 数据

**是什么。** 患者的信息和医疗记录。这是最敏感的一类内容。

**建议的做法：**

- 模块包里只放数据的结构说明（`data/schema.json`），实际数据只在实例数据目录里。
- 原件（PDF、图片、DICOM）原样保存，另外提取一份结构化数据。例如检验报告提取出「项目、数值、单位、参考范围、日期」，存进时间序列。
- Worker 通过工具读数据，不直接读文件。工具按权限返回需要的部分，并记一笔访问日志。
- 数据分级。例如「可以发到 Telegram 的」「只能在本机显示的」「只能给本地模型看的」。分级写在 schema 里，宿主执行，做法和盯盘提醒里「收据只在本机」一样。
- 导入是一个独立的动作：使用者拖进文件，或由 feed 送来。导入后由技能负责解读和归档。

**要讨论的问题：**

- 医疗数据要不要加密存放？用什么管钥匙？
- 哪些数据可以发给云端模型？这直接决定模型的选择，要和计费、隐私一起定。
- 数据损坏和误删怎么办？要不要自动备份？

### 5.3 领域工具

**是什么。** 确定性的计算，例如胰岛素敏感度、eGFR、CHA2DS2-VASc 评分、剂量换算。特点是结果必须准确、可以测试，不应该交给模型心算。

**建议的做法：**

- 每个工具是一个目录：`tool.json` 写输入、输出、单位、适用范围和引用的公式出处，`index.ts` 是代码，`cases.json` 是测试用例。
- 工具在子进程里运行，不能访问网络，不能读文件，只拿到输入，只返回输出。这是最容易做安全的一类代码。
- 宿主在安装模块时先跑一遍 `cases.json`，有一个不对就拒绝启用。
- Worker 通过一个统一的工具调用，例如 `domain_tool { name, args }`，推断任务也能用，因为它是纯计算。

**要讨论的问题：**

- 工具代码限定用 TypeScript，还是也允许 Python？Python 的计算库更全，但运行环境要另外准备。
- 工具要不要能调用另一个工具？

### 5.4 领域技能

**是什么。** 流程和做法：问诊、复诊、会诊、复核、跟踪。

**建议的做法：**

- 继续用 `skills/` 下的 Markdown，这一部分今天已经能用。
- 「关键指标的跟踪、趋势分析和预警」这一类需要的不只是技能。它要的是：一个指标的时间序列（数据）、一个或几个条件（越过阈值、连续上升、变化率）、一个提醒通道。这正好是盯盘条件（tripwire）在做的事，只是对象从股价换成了检验指标。建议把 tripwire 从行情里抽出来，做成宿主的通用能力：任何模块都能声明「我的数据里有哪些指标可以设条件」，提醒都走宿主行（ADR-0017）。
- 多学科会诊是一种协作方式，见 5.6。
- 报告复核（AI 看影像核对医生结论）要能看图，依赖模型的视觉能力，也依赖数据分级：影像能不能发给云端模型。

**要讨论的问题：**

- tripwire 什么时候通用化？现在这组 PR 先只做行情，通用化可以等第二个使用者（医疗指标）出现时再做。
- 技能要不要带版本和评测（`evals/`），改了技能能看出答得是更好还是更差？

### 5.5 Feeds

**是什么。** 外面有东西变了，要让 Super Agent 知道。医疗模块里有四种：网盘里的新报告、邮箱里的医院通知、智能设备的数据、某类药物的研究进展。

**建议先把 feed 拆成两层：**

- **连接器**：接一个外部服务的通用能力，例如 Google Drive、Gmail、IMAP、RSS、webhook 接收。连接器要处理授权（OAuth、密码）、限速、重试。它和领域无关，一个连接器供很多模块用。连接器属于宿主，或者是独立安装的「连接器包」。
- **领域 feed**：用某个连接器，盯某些东西，按领域规则解析。例如「Gmail 里发件人是某医院的邮件，附件是 PDF，提取成检验报告」。领域 feed 属于模块。

这样分开以后，大部分领域 feed 不需要写代码，写一份声明就够了（`module-code-and-feeds-memo.md` 的方向 D）。只有真正特殊的（例如解析某个设备厂商的数据格式）才需要代码，在子进程里运行（方向 C）。

**几个具体问题：**

- **webhook 需要开入站端口**，这和「家里的 Mac 不开端口」冲突。可以用 Tailscale 只在 tailnet 内接收，或者让设备数据先进云端，由 feed 定期拉取。
- **邮件和网盘是别人能写入的来源**，里面的内容一律只是数据，不能当成使用者的话（ADR-0003）。医院邮件里写「请立即停药」也只是数据。
- **研究进展跟踪**本质是定期搜索加去重加摘要，可以做成一个通用的「定期检索」连接器，模块只写检索词和筛选条件。

### 5.6 专家团队

**是什么。** 心内科、内分泌科、肿瘤科、影像科、临床药师这样一组成员，各有专长和技能。

**现状。** `agents/` 已经支持成员定义：工具、技能、模型，领队按需派活（ADR-0008）。

**要补的：**

- **协作方式。** 今天是领队一对一派活。多学科会诊需要「多位专家对同一份材料各自给意见，再由一位汇总，有分歧时点出来」。可以先做成一个技能，由领队按固定步骤派活和汇总；以后如果常用，再做成宿主的协作模式。
- **成员的数据权限。** 影像科医生要看影像，临床药师只需要处方和检验结果。成员的权限要能按数据分级来限。
- **免责和边界。** 每位专家都要知道自己不是真医生，结论要标明依据，涉及用药和急症的要明确提示就医。这写进模块的共同技能里，评测也要覆盖。

## 6. 模块能带代码，安全另行保证

详细讨论见 `module-code-and-feeds-memo.md`。这里只列和本备忘相关的结论：

- 模块里的代码（工具、带代码的 feed）都在子进程里运行，通过 socket 和宿主说话，不进宿主进程。
- 模块在清单里声明自己要什么：网络地址、密钥名字、请求额度、数据分级、要用哪些宿主能力。宿主只给声明过的。
- 第一次安装、或权限有变化时，宿主出一张确认卡片，使用者点了才启用。
- 审计分三档：内置模块随仓库审查；第三方审计过的带记录；没有审计的由宿主做基础扫描，结果写在确认卡片上。

## 7. 插拔和热插拔

### 7.1 模块的生命周期

建议把模块的状态做成一个明确的状态机，而不是散落的开关：

```
发现（目录里有它） → 校验（清单、文件、测试用例） → 等待确认（权限卡片） → 启用 → 运行中
                                ↓                         ↓                 ↓
                              无效（写明原因）          被拒绝            停用 → 卸载
```

- 每个状态都显示在页面上，带原因，例如「无效：tools/insulin-sensitivity 的测试用例 3 不通过」。
- 状态记在 `state.db` 里，宿主重启后保持。

### 7.2 热插拔要解决什么

不重启宿主就装上或拿掉一个模块，需要宿主在运行中做到下面几件事：

| 事情 | 现在 | 热插拔时要怎样 |
|---|---|---|
| 模块列表 | 启动时读一次，之后不变 | 一份运行中可以替换的模块表，替换是原子的 |
| 幕僚长的领域名单 | 启动时写进提示词 | 名单变化时更新幕僚长的提示词，或者每次注入当前名单 |
| 规则 | 启动时读 | 和模块表一起替换 |
| feed 和定时器 | 随宿主启停 | 每个模块的 feed 各自启停 |
| 工具和技能 | Worker 启动时按领域拿到 | 新任务用新版本；正在跑的任务继续用旧版本，跑完为止 |
| 正在跑的任务 | 领域被拿掉时，按没有领域的单个助手继续（ADR-0009） | 保持这个做法，并在任务上标明「所属模块已停用」 |
| 实例数据 | 没有 | 停用时保留，重新启用时接上 |

其中最难的是「正在跑的任务」和「feed 的游标」。建议的规则是：版本跟着任务走，任务开始时用的哪个版本，就一直用到结束。

### 7.3 更新

模块包有版本号。更新就是「装上新版本，停用旧版本」。如果新版本要的权限变多了，重新出确认卡片。实例数据的结构变了，由模块自带的迁移脚本处理。迁移脚本也在子进程里运行，失败就回滚到旧版本。

## 8. 让小白也能做出模块

### 8.1 三样东西

1. **模板。** 按领域的复杂程度分几种起步模板：只有知识和技能的、带团队的、带 feed 和数据的。`just module-new`（PR #27）扩展成可以选模板。
2. **模块制作工具（module builder）。** 它本身就是一个模块：一个专门帮人做模块的专家团队，和现在的 Pi专家队同一种做法。使用者用聊天说「我想做一个帮家人管理心衰的模块」，制作团队负责：
   - 问清楚领域的边界、要哪些知识、有哪些数据来源、需要哪些专家；
   - 生成模块包的骨架，填好清单、技能和专家定义；
   - 帮使用者导入知识文件，生成 `sources.json`；
   - 写出评测考题；
   - 跑校验和预演，把问题讲给使用者听。
3. **校验和预演。** `just module-check` 检查清单、文件、测试用例和权限；预演模式让模块在一个临时的状态目录里跑几个考题，不碰真实数据，不发 Telegram。

### 8.2 页面上的模块管理

建议在网页上加一页「模块」：

- 看到每个模块的状态、版本、它要的权限、它的 feed 是否正常、它占了多少实例数据。
- 启用和停用一个模块，确认权限卡片。
- 打开模块的实例数据，例如看到导入了哪些报告。

按 ADR-0003 的思路，「改规则要改文件」。模块的启用和权限确认是授权动作，要由宿主出卡片、使用者亲手点，这和 ADR-0010 的成员上限一样，需要一条新的 ADR。

## 9. 从现在走到目标，建议分几步

| 步骤 | 内容 | 依赖 |
|---|---|---|
| M0 | PR #27（开关、列表、新建骨架）已合并（cefb2c1）。补指南：来源的三种接法、宿主登记的 feed 清单 | 无 |
| M1 | 定下「模块包」和「实例数据」的分界，写 ADR；把自选股这类个人设置移出 `module.json` | M0 |
| M2 | 模块生命周期状态机和热插拔：运行中可替换的模块表、按模块启停 feed、任务版本跟着任务走 | M1 |
| M3 | 子进程运行模块代码：先做领域工具（最简单、无网络），再做带代码的 feed；权限清单和确认卡片 | M1，和 Worker 沙箱一起设计 |
| M4 | 连接器层和声明式 feed：先 RSS 和定期检索，再 Gmail、Google Drive | M3 |
| M5 | 知识检索和数据层：知识索引和 `knowledge` 工具；实例数据的结构、分级和访问工具；tripwire 通用化 | M1，M4 |
| M6 | 模块制作工具和网页上的模块管理页 | M2 到 M5 |
| M7 | 用医疗健康模块做第一个完整的试点 | M5，M6 |

每一步都可以单独上线，单独有用。M0 和 M1 小，可以马上开始。M2 和 M3 是架构上的大改动，各需要一条 ADR，并且要先做设计比较（pstack 的 `architect`）和对抗审查（`interrogate`）。

## 10. 建议的讨论顺序和要决定的事

建议按依赖顺序讨论，每次只定一件，定了就写成 ADR：

1. **模块包和实例数据的分界**（第 3 节）。这是其他一切的基础。
   - 实例数据放在哪里，按模块隔离到什么程度？
   - 卸载时默认保留还是删除？
2. **模块能带代码，以及代码在哪里运行**（第 6 节和 `module-code-and-feeds-memo.md`）。
   - 子进程加权限清单这个方向，同意吗？
   - 和 Worker 沙箱是不是一起做？
3. **生命周期和热插拔**（第 7 节）。
   - 热插拔是必须的，还是「停用后重启生效」也可以接受作为第一步？
   - 正在跑的任务用旧版本跑完，这个规则可以吗？
4. **连接器和领域 feed 的分层**（5.5 节）。
   - 连接器属于宿主，还是也可以单独安装？
   - webhook 怎么接，要不要开入站？
5. **数据分级和隐私**（5.2 节）。
   - 分几级？每级能去哪里（Telegram、云端模型、本地模型）？
   - 医疗数据要不要加密存放？
6. **知识检索**（5.1 节）。
   - 用不用向量检索？嵌入模型用哪个，怎么计费？
7. **tripwire 通用化**（5.4 节）。
   - 什么时候做？等第二个使用者出现，还是现在就规划接口？
8. **制作工具和管理页**（第 8 节）。
   - 制作工具做成一个模块（一个专家团队），同意吗？
   - 管理页上的启用和授权，是否按 ADR-0010 的方式由使用者亲手点？
9. **第一个试点模块**是医疗健康，还是先拿一个风险小的领域（例如 RSS 新闻跟踪）把架构跑通？

## 附：这份备忘没有覆盖的

- 模块市场和分发：怎么找到别人做的模块，怎么下载和更新。开源之后再讨论。
- 多个使用者共用一台宿主：现在的设计是一台宿主只服务一个人，实例数据也按这个假设设计。
- 模型的选择和计费：每个模块、每位专家用什么模型，会受数据分级影响，留到第 5 个决定时一起讨论。
