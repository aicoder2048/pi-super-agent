# 领域模块架构的需求清单

这份清单从 `docs/modules/module-architecture-upgrade-memo.md` 和 `docs/modules/module-code-and-feeds-memo.md` 整理而来。每条需求有一个编号。设计文档 `design.md` 必须逐条回应，`check.mjs` 会检查每个编号都在设计文档里出现。

## 目标

| 编号 | 需求 | 出处 |
|---|---|---|
| G1 | 加一个新领域不用改宿主代码。 | memo 第 1 节 |
| G2 | 模块能插拔。装上就有这个领域，拿掉就没有，最好不重启宿主。 | memo 第 1 节 |
| G3 | 不懂编程的使用者能从零做出一个模块。有模板，有制作工具。 | memo 第 1 节 |
| G4 | 一个领域需要的东西都能放进同一个模块。 | memo 第 1 节 |
| G5 | 安全和功能分开处理。不为了安全放弃模块的功能。 | memo 第 1 节，feeds memo 第 3 节 |

## 模块的六类组成

每一类都要在模块包里有固定的位置，在宿主里有对应的机制。例子取自个人医疗健康模块。

| 编号 | 组成 | 必须支持的例子 |
|---|---|---|
| K1 | 领域知识 | 几百页的指南、几十篇论文。按段落检索，回答带出处和版本。受版权保护的全文不进模块包。 |
| K2 | 数据 | 患者基本信息和医疗记录。原件加结构化提取。Worker 经工具读取，有访问记录，有数据分级。 |
| K3 | 领域工具 | 胰岛素敏感度这类确定性计算。有输入输出约定，有测试用例，没有 `bash` 的推断任务也能用。 |
| K4 | 领域技能 | 问诊、复诊、多学科会诊、报告复核、指标跟踪和越线预警。预警需要通用的条件机制。 |
| K5 | Feeds | Google Drive 的体检报告、邮箱里的医院邮件、智能设备数据、药物研究进展。分连接器和领域 feed 两层。 |
| K6 | 专家团队 | 一组专家，各有分工、技能和数据权限。支持多位专家对同一份材料会诊。 |

## 模块包和实例数据

| 编号 | 需求 | 出处 |
|---|---|---|
| I1 | 模块包只读，可以分享。宿主从不往模块包里写。 | memo 第 3 节 |
| I2 | 实例数据按模块隔离，放在状态目录下，由宿主管理访问。 | memo 第 3 节 |
| I3 | 卸载模块包时实例数据默认保留。重新启用时接上。 | memo 第 3 节，7.2 节 |

## 生命周期和热插拔

| 编号 | 需求 | 出处 |
|---|---|---|
| L1 | 模块的状态是一个明确的状态机。每个状态带原因，显示给使用者，宿主重启后保持。 | memo 7.1 节 |
| H1 | 运行中的模块表可以原子替换。 | memo 7.2 节 |
| H2 | 幕僚长的领域名单和规则跟着模块表变。 | memo 7.2 节 |
| H3 | 每个模块的 feed 和定时器各自启停。 | memo 7.2 节 |
| H4 | 新任务用新版本。正在跑的任务用开始时的版本跑完。 | memo 7.2 节 |
| H5 | 模块停用后，它正在跑的任务有明确的去向，并在任务上标明。 | memo 7.2 节 |
| H6 | 更新是装上新版本再停用旧版本。权限变多时重新确认。实例数据的结构迁移失败时回滚。 | memo 7.3 节 |

## 模块代码和安全

| 编号 | 需求 | 出处 |
|---|---|---|
| S1 | 模块的代码在子进程里运行，不进宿主进程。 | memo 第 6 节 |
| S2 | 模块在清单里声明要用的网络地址、密钥名字、额度、数据分级和宿主能力。宿主只给声明过的。 | memo 第 6 节 |
| S3 | 第一次启用或权限变化时，宿主出确认卡片，使用者亲手点了才启用。确认的是具体版本。 | memo 第 6 节，feeds memo 第 6 节 |
| S4 | 外部来源的内容只是数据，不是使用者的话（ADR-0003）。 | memo 5.5 节 |
| S5 | 能随时撤销。停用模块就停掉它的子进程，收回权限。 | feeds memo 第 6 节 |

## 制作和管理

| 编号 | 需求 | 出处 |
|---|---|---|
| B1 | 起步模板，按领域复杂程度分几种。 | memo 8.1 节 |
| B2 | 模块制作工具本身是一个模块，用聊天带使用者做出模块包。 | memo 8.1 节 |
| B3 | 校验命令和预演模式。预演不碰真实数据，不发 Telegram。 | memo 8.1 节 |
| P1 | 网页上有模块管理页。能看状态、版本、权限、feed 是否正常、实例数据占用，能启用和停用。 | memo 8.2 节 |

## 要给出答案的九个决定

memo 第 10 节列了九个要决定的事。设计文档要对每一个给出建议和理由，并标明哪些只有使用者能定。

| 编号 | 决定 |
|---|---|
| D1 | 模块包和实例数据的分界。实例数据放在哪里，隔离到什么程度，卸载时保留还是删除。 |
| D2 | 模块能带代码，代码在哪里运行。是否和 Worker 沙箱一起做。 |
| D3 | 生命周期和热插拔。热插拔是不是第一步就必须。正在跑的任务用旧版本跑完是否可以。 |
| D4 | 连接器和领域 feed 的分层。连接器属于宿主还是可以单独安装。webhook 怎么接。 |
| D5 | 数据分级和隐私。分几级，每级能去哪里。医疗数据要不要加密存放。 |
| D6 | 知识检索。用不用向量检索，嵌入模型怎么计费。 |
| D7 | tripwire 通用化。什么时候做。 |
| D8 | 制作工具和管理页。制作工具是否做成一个模块。启用和授权是否由使用者亲手点。 |
| D9 | 第一个试点模块是医疗健康，还是先用一个风险小的领域。 |
