# Pi Super Agent MVP 规格

> 状态：已与使用者确认（2026-11-08）。
> 术语以仓库根目录的 `GLOSSARY.md` 为准，难以反悔的决定见 `docs/adr/`，建造顺序见 `docs/pi-super-agent/implementation-log.md`。
> 设计来源：`docs/dsh-super-agent/super-agent-design-exploration.md` 及其开源原型文档。

## 问题

现在用 Pi 做事以会话为单位：一个会话一次只做一件事，做的时候不能接新指令，关掉终端它就停了，外部发生的事情（一封邮件、一条行情、一次 CI 失败）进不来。同时推进几件事时，使用者要自己开多个会话、自己记住每个会话的上下文，能并行多少件事取决于人的注意力。

## 方案

在 Pi 之上建一个个人使用的 Super Agent。使用者始终只面对一个 Agent：随时对它说话，它立即回应并在后台并行推进多项任务；外部事件能驱动它工作；关掉界面它继续运行，进程重启后任务接着做。

MVP 在 MacBook 上验收。之后的第一个里程碑是搬到家里的 Mac mini 上 7×24 运行，长期方向是能接入业务模块（邮件、X 资讯、看盘）的平台。

### 验收演示

1. 使用者在客户端提任务 A，Router 一句话确认并派出 Worker A。
2. 使用者不等待，接着提任务 B，Router 派出 Worker B。
3. 一条外部触发落到任务 A 订阅的线程，不经过 Router 的模型调用，直达 Worker A。
4. Worker A 汇报，Router 用一句话把结果告诉使用者。
5. 杀掉宿主再启动，任务和会话都还在，未完成的任务接着做。
6. 玩具模块投递一条命中规则的触发，Router 自动开任务；Worker 判断无需处理时全程安静。

## 用户故事

### 对话与并行

1. 作为使用者，我想随时对 Super Agent 说话并立即得到回应，这样上一件事没做完也不耽误我交代下一件。
2. 作为使用者，我想同时推进多项任务而不用自己开多个会话，这样并行的数量不受我的注意力限制。
3. 作为使用者，我想只面对一个 Agent，这样我不用记“哪个会话里有哪段上下文”。
4. 作为使用者，我想说“刚才那个改成方案 B”就能改动正在进行的任务，这样我不用指明任务编号。
5. 作为使用者，我想让 Router 的每条回复不超过 200 字，这样我一眼就能看完。
6. 作为使用者，我想让 Router 确认一次之后保持安静，只在有结果、要我做决定或做不下去时才说话，这样我不被过程打扰。
7. 作为使用者，我想在 Worker 需要我做决定时只收到一个具体的问题，这样问题不会埋在长报告里。
8. 作为使用者，我想随时叫停某个任务，这样方向错了能立刻止损。

### 事件驱动

9. 作为使用者，我想让任何脚本都能向 Super Agent 投递触发，这样还没有专门来源的事件也能进来。
10. 作为使用者，我想让定时器产生触发，这样可以安排周期性的检查。
11. 作为使用者，我想让同一线程上的后续触发直达正在处理它的 Worker，这样后续进展不需要我再提一次。
12. 作为使用者，我想用自然语言写规则，说明哪类触发值得开任务，这样没人开口时 Super Agent 也知道该做什么。
13. 作为使用者，我想让明显无关的触发在调用模型之前就被筛掉，这样不为噪音花钱和时间。
14. 作为使用者，我想让 Router 在没有规则时也能自行判断某件事值得做，这样它能发现我没想到的事。
15. 作为使用者，我想让依据为推断的任务先悄悄做、没价值就不打扰我，这样主动性不变成噪音。
16. 作为使用者，我想让依据为推断的任务不能自行发邮件、发帖或推代码，这样它判断错了损失也有限。
17. 作为使用者，我想提起一件旧事时 Router 能顺着记录找回上下文，这样长期运行后它不会忘事。

### 可见性

18. 作为使用者，我想在看板上看到每个任务的阶段和最近一条汇报，这样我知道现在有哪些事在等我。
19. 作为使用者，我想看到每个 Worker 用的模型、工具调用次数、token 用量和已运行时长，这样我知道钱和时间花在哪里。
20. 作为使用者，我想只读地翻看某个 Worker 的完整过程，这样出问题时我能查清原因。
21. 作为使用者，我想看到每条触发的去向（被筛掉、被转交、开了任务、被忽略），这样我能调整规则。

### 持久与可靠

22. 作为使用者，我想关掉客户端后 Super Agent 继续运行，这样它不依赖我开着终端。
23. 作为使用者，我想宿主重启后任务、订阅和会话都还在，这样一次崩溃不会让工作白做。
24. 作为使用者，我想让宿主停机期间投递的触发在恢复后被处理，这样事件不会丢。
25. 作为使用者，我想在宿主无响应时有东西自动把它拉起来，这样不用我半夜去重启。
26. 作为使用者，我想在某个 Worker 长时间没有进展时得到通知，这样卡死的任务不会无声无息。
27. 作为使用者，我想让发给 Worker 或发给我的消息失败后自动重试，这样偶发故障不需要我介入。

### 成本与安全

28. 作为使用者，我想让所有模型调用默认走 Codex 订阅，这样日常运行不产生按量费用。
29. 作为使用者，我想在 Codex 额度用尽或限流时自动回退到 DeepSeek，这样 Super Agent 不会停摆。
30. 作为使用者，我想给按量计费的回退设每日用量上限，这样无人值守时出错的代价是有限的。
31. 作为使用者，我想让系统在代码层面拒绝 Anthropic 的模型，这样不会再误用按量计费的 API。
32. 作为使用者，我想让来源带进来的内容只被当作数据，这样别人写在邮件或推文里的指令不能指挥我的 Agent。
33. 作为使用者，我想让规则只能由我自己编辑文件来改，这样 Router 被诱导时也无法扩大自己的权限。

### 扩展

34. 作为使用者，我想加一个模块时不改内核，这样邮件、X 资讯、看盘可以逐个接入。
35. 作为使用者，我想以后用桌面端或手机端连接同一个宿主，这样人机界面可以独立演进。
36. 作为使用者，我想把整个状态目录复制到 Mac mini 就能继续运行，这样迁移不需要重建。

## 实现决定

### 整体结构

- **宿主**是一个不依赖终端的进程，是唯一的组装点：它打开存储、启动来源、持有 Router、管理 Worker、接受客户端连接。见 ADR 0001。
- **Router** 是宿主进程内的一个 Pi 会话；每个 **Worker** 是一个独立的 Pi 子进程。见 ADR 0002。
- **Watchdog** 是宿主之外的独立进程。
- **客户端**是一个 Pi TUI 加一个很薄的扩展，通过本机连接与宿主通信。

### 模块划分

| 模块 | 职责 | 依赖 Pi |
|---|---|---|
| 内核 | 领域规则：接收触发、过滤、订阅扇出、任务生命周期、依据与限制、汇报处理。它是触发、线程、任务、订阅的唯一写入者 | 否 |
| 存储 | 一个 SQLite 文件上的读写，以及待执行动作的队列 | 否 |
| Router 适配 | 把内核产生的通知注入 Router 会话，把 Router 的工具调用翻译成内核命令 | 是 |
| Worker 执行器 | 为任务准备目录、拉起和结束子进程、投递输入、读取事件流和统计 | 是 |
| 来源 | 通用来源、定时器、对话来源，各自把外部事件翻译成触发 | 否 |
| 渠道 | 把 Router 的回复写回对应线程；MVP 只有对话渠道 | 否 |
| 客户端扩展 | 转发使用者输入，显示回复和看板 | 是 |
| 模型选择 | 为每个会话决定模型，处理回退、用量上限和禁用名单 | 部分 |
| Watchdog | 定时检查并介入 | 否 |

内核通过端口依赖外部：存储、执行器、Router 通知、渠道、时钟。内核的方法是同步的，每条命令在一个事务内完成；对外动作先记入队列，事务提交后再执行（先存后做）。

### 一条触发的去向

1. 来源把外部事件翻译成触发，指明它属于哪些线程，交给内核。同一条触发提交两次只存一次。
2. 程序层过滤：按来源的配置把触发定为“忽略”或“候选”。被忽略的触发只留记录。
3. 订阅扇出：线程上有订阅它、且还没结束也没被叫停的任务时，触发直接作为输入送给这些任务的 Worker，不经过 Router 的模型调用。
4. 没有被任务接走的候选触发送给 Router，由它对照规则决定：开任务、转交、忽略。
5. 每条触发的去向都留有记录。

**对话**是一个例外：它是一个线程，但不被任何任务订阅，其中每句话都到 Router。Router 可以把一句话转交给已有任务。

### 任务

- 只有 Router 的决定能创建任务。任务创建时记下它的依据，之后不变。
- 任务的阶段由它在等什么决定，从上往下第一条命中的为准：

| 阶段 | 条件 |
|---|---|
| 等你回答 | Worker 提了一个问题，尚未回答 |
| 等你验收 | 最近一条汇报是“就绪” |
| 受阻 / 失败 | 最近一条汇报是“受阻”或“失败”，之后使用者没有再说话 |
| 排队 | 还没有 Worker，或在等空位 |
| 空闲 | Worker 一轮结束，没有未答的问题 |
| 执行中 | 其他情况 |

- 汇报“无需处理”直接结束任务，默认不发消息。汇报“就绪”且不再等待任何线程时任务结束。结束的任务保留订阅记录和会话，使用者再提起时可以恢复。它订阅过的线程再来新触发时，不再直达它，而是照常经过程序层过滤，作为候选交给 Router；Router 对照规则开新任务，或者把触发转交回这个任务，转交后任务重新打开。
- 使用者叫停的任务不再接收任何输入。

### 依据与限制

| 依据 | 来自 | 能做到哪一步 |
|---|---|---|
| 请求 | 使用者在对话里直接开口 | 请求范围内的一切 |
| 规则 | 触发命中使用者写的某条规则 | 规则允许的范围 |
| 推断 | Router 自己判断值得做 | 只产出草稿和结论，不做对外动作 |

对依据为推断的任务，以下限制由程序执行，不靠提示词（见 ADR 0003）：

- 开始时不发确认；汇报“无需处理”时不发任何消息。
- 同时运行数和每日总数有上限，超出时 Router 的开任务决定被拒绝并留记录。
- 对外动作被拦截，只能以草稿形式随汇报提交，等使用者确认。
- 可以用 `web_get` 读公网网页：只发 GET，拒绝本机和内网地址，限时限量，网页内容只当数据。GET 的网址能带出数据，这一风险已接受。

只有两样东西能授权：使用者在对话里的话，和使用者写在文件里的规则。来源内容一律只是数据。规则文件由宿主在启动和重新加载时读入 Router 的提示词，Router 没有写规则的工具。

### Router

- 工具只有五类，没有执行命令、读写文件的工具：

| 工具 | 用途 |
|---|---|
| 读取 | 按 id 读任务、线程、触发及其相邻内容；返回结果里带下一跳对象的 id |
| 路由 | 一次提交一到多个决定：开任务、转交、忽略、叫停 |
| 回复 | 通过某个线程的渠道对使用者说话 |
| 备注 | 把别处得来的一条事实告诉某个任务的 Worker，不构成授权 |
| 问状态 | 让一个空闲的 Worker 报告现状 |

- 路由工具立即返回。拉起 Worker 是排入队列的动作，不占用 Router 的这一步。
- Router 的消息队列设为“全部送达”：它推理期间积压的触发和汇报在下一次模型调用时一并注入，形成批处理。
- 注入 Router 的每条消息都带明确的类型标记（对话、候选触发、Worker 汇报、Worker 提问、通知），因为 Pi 把注入的消息一律当作用户消息交给模型。只有标记为“对话”的消息代表使用者本人。
- 触发以卡片形式注入：id、来源、线程、发出者、时间、正文开头、相关任务的 id。超过长度上限的部分不注入，只给读取入口。
- Router 的回复有字数上限，由回复工具强制执行。
- Router 的会话开启自动压缩和自动重试，不受使用者全局 Pi 设置影响。

### Worker

- 每个任务一个 Worker、一个独立的工作目录、一个确定的会话 id。模块可以提供一条准备命令，在第一次启动前运行一次。
- Worker 拥有 Pi 的标准工具，另加：

| 工具 | 用途 |
|---|---|
| 汇报 | 提交结构化状态：进展、就绪、受阻、失败、无需处理；可附带一个要问使用者的问题 |
| 交回 | 把一条超出本任务范围的输入交还给 Router |
| 读取 | 读本任务及其线程的内容，读不到别的任务 |
| 后台命令 | 启动、查看、停止一条长时间运行的命令；启动立即返回，命令结束时结果作为新输入送回 |

- Worker 的推理过程和工具调用不进入任何渠道，只有汇报到达 Router。
- Worker 空闲时子进程退出，会话留在磁盘上；有新输入时按会话 id 重新拉起。
- 一轮结束时如果还有后台命令在跑，任务保持“执行中”并继续占用名额，直到命令结束或超过最长时间。
- 同时运行的 Worker 有上限，另留一个名额给依据为请求的任务和使用者的后续消息，保证新工作不会挡住使用者继续已有的任务。
- MVP 的 Worker 以使用者的系统用户身份运行，命令不需要批准，没有沙箱。工作目录是默认约定，不是安全边界。

### 来源、渠道与模块

- **通用来源**监视状态目录下的一个投递目录。外部脚本放入一个文件即投递一条触发，文件里指明线程标识和正文。宿主停机期间放入的文件在恢复后被处理。
- **定时器来源**按配置的时间表产生触发。
- **对话来源与渠道**承载客户端连接。
- 以后的平台（GitHub、邮件、Telegram）各自实现来源和渠道，在宿主内运行，直接把触发交给内核，不经过投递目录。
- **模块**是一个目录，包含来源配置、规则文件和 Worker 用的技能。宿主启动时发现并加载模块，加模块不改内核。MVP 带一个玩具模块：脚本定时投递假的行情触发，配一条规则。

### 客户端

- 客户端扩展拦截使用者的输入并转发给宿主，本地的模型不参与。
- 宿主把 Router 的回复、看板数据和 Worker 的过程流推给客户端。
- 看板每个任务一张卡片：标题、阶段、依据、最近一条汇报、模型（含是否已回退）、工具调用次数、token 用量、已运行时长。
- 使用者可以只读地打开某个 Worker 的完整过程，不能直接对 Worker 说话。
- 客户端与宿主之间的协议不含任何 Pi TUI 特有的内容，以后供桌面端和手机端复用。

### 模型与计费

| 角色 | 模型 |
|---|---|
| Router | `openai-codex/gpt-6.1-terra` |
| Worker | `openai-codex/gpt-6.1-sol` |
| 回退 | `deepseek/deepseek-flash` |

- 遇到额度或限流错误，重试三次后切到回退模型，并通知使用者一次。回退期间每 15 分钟在新一轮开始时试一次主模型，成功则切回。
- 回退模型的用量按日累计。超过上限时，Worker 汇报“受阻”并停下；Router 继续使用回退模型，因为它必须保持能回应。
- 模型选择模块拒绝任何 `anthropic` 提供方的模型，无论配置里怎么写。

### 状态与恢复

- 全部状态在一个状态目录里：数据库、Worker 的工作目录、会话文件、投递目录。目录位置可配置，不放在代码仓库内。
- 数据库记录：触发及其去向、线程及其订阅、任务及其汇报和输入、待执行动作、回复的发送回执、来源的读取位置、用量统计。
- 待执行动作失败后按递增的间隔重试；同一类动作连续失败三次才算系统问题。
- 宿主重启时，正在执行的任务重新拉起 Worker，并附一段恢复说明，要求它先检查自己的工作目录再决定是否重复对外动作。等使用者的任务保持原状。

### Watchdog

- 定时检查三件事：宿主是否在更新心跳；每个执行中的任务距上次进展多久；是否有连续失败的待执行动作。
- 宿主无心跳时重启它。
- 发现卡住的任务或系统问题时，通过通用来源投递一条触发，由 Router 告诉使用者。这样 Watchdog 不需要自己的渠道。
- MVP 的 Watchdog 只做确定性检查，不调用模型。

### 默认数值

全部可配置。

| 项目 | 默认值 |
|---|---|
| 同时运行的 Worker | 3 个，另留 1 个名额 |
| 依据为推断的任务 | 同时 1 个，每天最多 24 个 |
| Router 单条回复 | 不超过 200 字 |
| Worker 一轮结束后后台命令的最长时间 | 120 分钟 |
| 回退模型的每日用量 | 输入加输出合计 800 万 token |
| Watchdog 检查间隔 | 3 分钟 |
| Worker 无进展算异常 | 30 分钟 |
| 模型错误重试 | 3 次 |
| 回退后试探主模型的间隔 | 15 分钟 |

### 技术选择

- TypeScript，由 Node 直接运行，不加构建步骤。
- 存储用 Node 自带的 SQLite，测试用 Node 自带的测试运行器，命令入口用 `just`。
- 除 Pi 本身外不引入新的运行时依赖。

## 测试决定

- 好的测试只验证外部行为：给定一串触发、决定和汇报，检查任务的阶段、触发的去向、排入队列的动作，不检查内部结构。
- 测试接缝有三个，尽量用最高的那个：

| 接缝 | 测什么 | 怎么隔离 |
|---|---|---|
| 内核的命令入口 | 过滤、扇出、任务生命周期、依据限制、恢复规则 | 内存数据库、假时钟、假的执行器和渠道 |
| 宿主的组装点 | 一条请求从对话到 Worker 再回到对话；批处理；重启恢复 | 脚本化的假 Router 和假 Worker，不调用真实模型 |
| 真实模型冒烟 | 验收演示的六步 | 手动运行，不进自动测试 |

- 涉及时间的规则（重试间隔、每日上限、无进展判定）一律通过假时钟测试，测试保持确定性。
- 先例：`tests/now.test.mjs` 的写法，以及 `src/pi-runtime.mjs` 解析全局 Pi 依赖的方式（`tests/pi-runtime.mjs` 只是转发到它）。

## 不在范围内

- 第二个渠道：Telegram、微信、GitHub 评论、邮件回复。
- 真实的平台来源：GitHub、邮件、X、行情。
- 上云、端侧 daemon、跨设备执行环境。
- 部署到 Mac mini：开机自启、崩溃自动拉起的系统托管、远程连接。
- 由模型判断方向是否跑偏的 Watchdog 会话。
- 多用户、白名单、跨来源的身份映射。
- Worker 沙箱。条件是：接入第一个会读外部内容的模块之前必须先补上。
- 使用者直接对 Worker 说话；在客户端点选任务作为快速通道。
- 桌面端和手机端。
- Router 的水平切分、Worker 之间的直接通信。
- 旧记录的清理：数据库在 MVP 里只增不减。

## 备注

- 三件事 Pi 文档没有明确保证，需要在动手前验证：被中断的 Worker 会话能否续上；Pi TUI 能否当薄客户端；Router 的批处理注入是否如预期。任何一项不成立都要回头修改本规格，见 `docs/pi-super-agent/implementation-log.md` 第 0 步。
- 使用者的全局 Pi 设置关闭了自动压缩和自动重试，宿主的会话必须自行开启。
- Pi 没有内置的跨提供方模型回退、后台命令、调度器，这三样都由本项目实现。
