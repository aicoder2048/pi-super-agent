# MVP 审计整改：figure-it-out 工作设计

使用者的目标：按 `mvp-spec.md` 和 `IMPLEMENTATION_PLAN.md` 交付 Pi Super Agent 的 MVP，并且每一步都留下 pstack 要求的证据。
之前 Stage 0 到 4 已有代码和提交，但没有按 pstack 完整执行（没有设计评审、没有先红后绿、没有决策记录、直接提交到 main）。
这一轮是审计加整改，不推倒重写。决策记录在 `decisions.tsv`。

## Phase A：定框

### 完成的判定（每条都可证伪）

| 编号 | 判定 | 证据 |
|---|---|---|
| P1 | `just test` 在分支头连续三次全部通过 | 三次运行的输出 |
| P2 | 验收演示六步在真实 Pi TUI 里用真实 Codex 模型全部通过 | tmux 截屏文本存到 `docs/pi-super-agent/evidence/` |
| P3 | 规格 36 条用户故事逐条对应到一个自动测试或一次真实检查；做不到的写明原因 | `story-trace.md` |
| P4 | `interrogate` 每条经复现确认的发现，都先写失败的测试再修，或写明暂缓理由 | 测试名、修复提交 |
| P5 | Stage 5 验收标准逐条满足：Watchdog 拉起宿主、卡住通知、限流回退与切回、每日上限、宿主会话自带压缩与重试 | 自动测试加真实检查记录 |
| P6 | `mvp` 分支开出 PR，决策记录随 PR 提交，提交前做过删注释和去冗余检查 | PR 链接 |

### 规模

- 生产代码约 4000 行，测试约 1800 行，134 个测试。
- Stage 5 有 269 行未提交改动。其中三处接线没有先写测试（`src/host/main.ts` 的模型接线、`src/watchdog/main.ts`、Router 提示词里关于 Watchdog 的一句），已另存补丁，整改时撤掉重做。

### 风险等级：高

- 宿主无人值守运行。授权边界（ADR 0003）一旦出错，就是 Router 或 Worker 越权做了对外动作，事后很难收回。
- 按量计费的回退模型可能在无人时持续消耗费用。
- 重启恢复处理不当会丢任务，或者重复做对外动作。

因此有争议的设计都要经过多模型对抗审查，所有修复都先写失败的测试。

## Phase B：工作设计

按“风险最大、最不确定的先做”排序。每个单元以一次可复查的检查结束，通过后才进入下一个。

1. **独立解读。** 用 `how` 让四个探查员加一个讲解员给出系统的独立说明，不以我写的代码说明为准。产出 `how.md`。
2. **对抗审查。** 用 `interrogate` 审查整个分支。每条发现必须有复现命令和输出。重点审 Router 的批量注入、授权边界、动作队列与重启恢复、模型回退。
3. **撤回未测接线，按 TDD 重做。** 先撤掉那三处接线。为每处写失败的检查（入口接线用启动冒烟脚本，提示词用宿主层测试），确认是红的，再写实现。
4. **逐条修复确认的发现。** 每条都是一个单元：先写失败的测试，看它红，修，看它绿，提交。发现之间互不影响的，可以分给不同 Worker 在各自的 worktree 里做。
5. **用户故事对照。** 36 条故事逐条找到对应的测试或真实检查，缺口按第 4 步的方法补。
6. **Stage 5 真实检查。** Watchdog 拉起被杀的宿主；把阈值调低，验证卡住通知；用无效的主模型配置模拟限流，验证回退与通知。
7. **完整验收。** tmux 驱动真实 TUI 走六步，截屏存档。
8. **收尾。** 删注释检查（`no-comments`）、去冗余检查（`simplify`，代替没有安装的 `deslop`）、决策记录对照会话记录自查、换一个模型族复核记录、开 PR。

### 不做的事

- 不重写 Stage 1 到 4 已经通过真实验证的代码。只修 `interrogate` 和故事对照找出的问题。
- 不为同一个已定的设计再跑一轮 `arena`。只有第 2 步发现需要改设计时，才对那一处跑 `architect`。
