# IM 私聊里、名单上的账号就是使用者

2026-11-11 在使用者授权的无人值守运行中拟定，使用者合并即确认。回答 ADR-0009「以后」一节留下的「谁算使用者」；修订 ADR-0010 里回答成员上限的渠道；补充 ADR-0004：对话可以经过使用者选定的 IM 服务。

## 问题

使用者想在手机上通过 Telegram 和白宫对话。网页和终端都在本机或使用者自己的 tailnet 上，靠状态目录里的 token 认人（ADR-0004、ADR-0007、ADR-0014）。Telegram 不一样：机器人谁都能搜到、谁都能发消息，消息先到 Telegram 的服务器，再由宿主取回。所以要先说清楚，哪条 IM 消息算使用者的话，其余的怎么处理，以及哪些内容会离开本机。

## 决定

**谁算使用者。** 一条 IM 消息算使用者的话，当且仅当三条同时成立：它经宿主自己运行的 IM 客户端进来；它在私聊里；发信人的平台数字 id（Telegram 的 `from.id`）写在 `config.json` 该平台的名单里（`telegram.allowedUserIds`）。用户名和显示名会变，不算。名单只能由使用者改文件，不做聊天里的配对码，和「规则只能改文件」同理。

**其余一律在交给内核之前丢弃。** 陌生人、群、频道发来的消息：不回复，不写触发，不进 Telegram 自己的表。日志最多每小时一行，只写丢弃了几条，不写对方 id 和内容。

**设置模式。** 名单是空数组时，客户端只告诉私聊来信的人他自己的数字 id，每个聊天一次，仍然什么都不交给内核。使用者靠它找到自己的 id，不用借助第三方机器人，宿主也不用把陌生人的 id 写进日志。

**名单上的人说的话。** 他在私聊里打的字就是使用者在对话里说的话，和网页、终端是同一个对话。转发的消息不算使用者的话（理由同 ADR-0011：那是别人的话），图片、语音等非文字消息也不交给幕僚长，客户端各回一句说明。`/start` 和 `/help` 回一段说明；别的以 `/` 开头的字当作普通的话。网页和终端说的话静默转到 Telegram，前面写「你在网页或终端说：」，这样手机上的聊天是完整的对话。

**ADR-0010 修订。** 成员上限仍只能在网页和终端放宽。IM 客户端只发一条说明，指向网页或终端的「待你处理」，不给按钮。宿主对来自 IM 的成员上限回答一律拒绝，拒绝原因是 `not_here`，不靠客户端自觉，以后的其他 IM 客户端也忘不掉。问题卡片变成 Telegram 按钮的那一版同时加上了宿主的拒绝：`Host.answer` 带着 IM 来处收到成员上限的编号时回 `not_here`，Telegram 客户端也从不给成员上限做按钮，伪造的按钮回调在客户端就被拒（`tests/cap-ask.test.ts`、`tests/telegram.test.ts`）。

**ADR-0004 补充。** 写了 `telegram` 段，就是使用者同意这些内容经过 Telegram 的服务器：他在 Telegram 说的话、幕僚长的回复、转过去的网页和终端的话，以及以后的问题卡片。执行过程、看板细节和成员的输出不发。机器人聊天不是端到端加密的。

**只有出站连接。** 客户端用 Bot API 的长轮询取消息，宿主不开任何入站端口，不用 webhook。

**bot token 只在宿主里。** token 放在 `secretsFile` 或环境变量 `TELEGRAM_BOT_TOKEN` 里，不进 `config.json`。名字以 `_TOKEN` 结尾，所以不进 Worker 的环境（ADR-0005）。宿主里只有 Bot API 客户端一个对象拿得到它；打印、转 JSON 都只显示 `[BotToken]`；报错只由固定的部分和 Telegram 的说明拼成，不带网址；日志只写 token 来自哪里。Bot API 的地址只能是官方地址或 `http://127.0.0.1:<端口>`，后者只给测试用，`config.json` 里没有改它的设置。

## 已知风险

- **有 `bash` 的 Worker 读得到 `secretsFile`，也就读得到 bot token。** 这和 ADR-0007 的 `client-token` 是同一个限度，但后果更重：拿到 token 的人可以抢先取走使用者之后发给机器人的消息，也可以冒充机器人发消息。Worker 沙箱落地时必须把 `secretsFile` 挡在外面。
- **Telegram 账号被盗等于使用者被冒充。** 这和网页 token 泄露是同一类风险。使用者自己保管手机，并给 Telegram 开两步验证。
- **一条回复正在发的时候宿主被杀掉**，重启后这条可能在 Telegram 上出现两次。正常停止时宿主会等它发完（最多 5 秒）。

## 没有采用的做法

- **聊天里的配对码。** 模型读到的内容可能诱导使用者完成配对；改文件才是授权。
- **按用户名认人。** 用户名可以改，也可以被别人注册。
- **接群聊。** 群里的话是别人的数据，那是来源，要另行设计。
- **webhook。** 要开入站端口。
- **每个任务一个私聊话题。** 和「只面对一个对话」相反。
- **MarkdownV2 格式。** 转义规则严，回复又是短句，发纯文本。

## Consequences

- 去掉 `telegram` 段，Telegram 客户端就不运行。写了这一段却没有 token，或 token 格式不对，宿主启动时就报错退出，报错里没有 token。
- Telegram 拒绝 token（401）时，只有 Telegram 客户端停用，日志一行说明；网页和终端照常。
- 名单里去掉某个 id 后重启，宿主删掉这个聊天在 Telegram 表里的记录。换成另一个机器人的 token（冒号前的数字变了），Telegram 的全部记录一起清掉。
