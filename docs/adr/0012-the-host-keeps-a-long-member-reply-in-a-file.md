# 成员的长回复由宿主存成文件

成员的回复原来超过 2000 字就截断。Pi专家队的两个真实任务里，`ext-expert` 一次派活读了三十多万字符的文档，只能交回 1800 字，助手拿这点内容写不出代码，于是自己又把 `extensions.md` 读了 4 遍、`types.d.ts` 读了 5 遍。回复太短，省下的 token 又在助手那边花回去了。

现在回复超过 2000 字时，宿主把全文写进任务目录的 `replies/<成员>-<序号>.md`，序号按这位成员在这个任务里已有的文件往下数。助手拿到的仍是前 2000 字，放在随机边界里；边界外由宿主写明全文多少字、文件在哪、要用时用 `read` 读，全文同样只是数据，不是指令。页面上这次派活的回复也只显示前 2000 字，末尾写明全文字数和路径。写不了文件时退回原来的截断，并写明没存下的原因。

成员的提示词跟着改：开头先写结论摘要，完整内容（代码、数据、出处）放在后面，不整篇照抄文档。Pi 专家的摘要不超过 1500 个字符。

## 为什么由宿主写，不让成员写

成员的工具由任务的依据决定（ADR-0003）：推断出来的任务里成员只读，Pi专家队九位专家的工具清单里也没有写文件。让成员自己把结果写进文件，要么给只读的成员开一个写文件的口子，要么只有能写文件的任务才有这条出路。宿主本来就收着成员的最后一条回复，由它落盘，成员的权限一点不变，所有任务都适用，文件名和位置也由宿主定，成员指定不了。

## 没有采用的做法

- **把上限调大**：长回复全部进助手的上下文，之后助手的每一轮都带着它，用不到的部分也在。存成文件后，助手只在需要时读。
- **给成员一个写结果的工具**：见上一节。
- **宿主替成员写摘要**：要再调一次模型，摘要也不一定是助手要的那部分。摘要由成员自己写在开头。
