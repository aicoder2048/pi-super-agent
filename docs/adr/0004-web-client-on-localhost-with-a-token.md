# 网页客户端只开在 127.0.0.1，靠网址里的 token 和 Host 头校验

宿主在 `127.0.0.1` 上开一个 HTTP 网关（端口取 `config.json` 的 `webPort`，默认 4517），浏览器用 SSE 收到的消息和 Unix socket 客户端完全相同。token 是 32 字节随机数，存在状态目录的 `web-token` 里，宿主每次启动读它，没有或内容不对才生成新的；宿主日志打印 `[host] 网页 http://127.0.0.1:4517/?token=…`，只有带对的 token 才能拿到页面和事件流。四个静态文件 `/app.mjs`、`/view.mjs`、`/client/board-format.mjs` 和 `/icon.svg` 不含对话、任务数据或 token，所以不要 token，只查 Host 头。请求地址解析不了的直接 400；其余每个请求先查 `Host` 头，必须是 `127.0.0.1:<端口>` 或 `localhost:<端口>`，否则 403；然后才比对 token（常数时间比较），不对就 401。

只绑本机，是因为宿主持有全部对话和任务，网页没有登录体系，不该让局域网里的其他设备看到。光绑本机还不够：本机浏览器里打开的任何网站都能向 `127.0.0.1` 发请求，DNS rebinding 还能让恶意域名解析到 `127.0.0.1`、绕过同源限制读到响应。token 挡住前者，Host 头挡住后者（rebinding 的请求带的是恶意域名），而且 Host 头先于 token 检查，让这类页面连 token 猜没猜对都得不到反馈。

token 放在网址里，不放 cookie。cookie 不按端口隔离：`127.0.0.1` 上任何端口的服务都会收到它，而且浏览器会自动带上它，这正是 W2 加写操作后要防的 CSRF。网址里的 token 只有拿到日志的人才有。页面用 `no-referrer` 和 `no-store` 防止 token 经 Referer 或缓存泄出，CSP 只允许同源脚本，页面上的文字一律用 `textContent` 渲染。

我们接受 token 出现在宿主日志、浏览器地址栏和历史记录里。能读这些的人本来就能读宿主的状态目录。宿主日志 `host.log` 由 Watchdog 以 0600 创建，已有的文件权限更宽就先收紧到 0600 再拉起宿主；宿主或配置加载时新建的状态目录是 0700，使用者自己建好的目录权限不动。

token 跨重启不变，这样 Watchdog 拉起崩溃的宿主后，开着的网页自己重连，不用去日志里找新网址。`web-token` 创建时就是 0600（先写临时文件再改名），发现权限更宽就收紧到 0600 并记一行日志。能读到它的人也能连同一目录下的 `host.sock`，所以暴露面没有变大。要换 token 就运行 `just web-token-rotate`：它删掉 `web-token`，宿主下次启动生成新的，旧网址随之失效；正在运行的宿主沿用旧 token，直到重启。

## Considered Options

- **cookie 携带 token**：刷新和书签更方便，但 cookie 不按端口隔离，又会被浏览器自动带上，W2 有了 POST 之后就是 CSRF 的入口。
- **不要 token，只绑本机加 Host 头校验**：挡得住 rebinding，挡不住本机其他用户和本机上跑的其他程序。
- **每次启动换新 token**：日志泄露的网址只活到下次重启，但每次重启都要使用者手动换网址，Watchdog 的自动拉起在网页这边就不算数了。
- **网关做成独立进程，连 `host.sock`**：宿主不用改，但要多开一个窗口，违背「一个标签页」的目标。

## Consequences

- 唯一的写入口是 `POST /say`。它在 Host 头和 token 之外，还要求 `Origin` 恰好是本机这个端口的页面（缺失也拒绝，403），正文必须是 `application/json`（否则 415）。跨站页面发 JSON 要先过 CORS 预检，而网关从不回应预检，所以这是 `Origin` 之后的第二道墙。
- 第二个 `just host` 会因为端口被占用而退出，不再抢走正在运行的宿主的 `host.sock`。启动宿主的测试一律用 `webPort: 0`。
