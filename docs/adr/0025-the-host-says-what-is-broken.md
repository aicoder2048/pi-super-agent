# 断了由宿主说，不由模型说

2026-11-13 按使用者的要求拟定：「数据断了不告诉我，这个不行！」无论是取不到交易数据，还是调不通大模型，界面上都要看到警告，好及时去修。

## 问题

这之前，断开有三种下场。模型出 5xx、太忙、连不上、401 时，幕僚长在后台退避重试，使用者什么都看不到。主模型限流切到回退模型时，宿主让幕僚长「用一句话告诉使用者」，可幕僚长自己的模型断了的时候没人能说。模块 feed 报的 `problem` 写一条「通知」宿主行（ADR-0020），但 handler 抛错、超时的 feed 什么都不写，而且通知行会被后来的对话冲走，修好了也没有一句「好了」。

## 决定

**宿主的代码记下每一处断开，叫警报（Alarm）。拉响和解除都由宿主的代码做，模型不参与。**

- 一处断开一个编号：`model:router`、`model:worker`、它们的 `:fallback`、`model:fallback-cap`、`data:<来源>`。同一个编号正在响时，再失败只加次数、换最近的错误。
- 网页在页头下一直显示正在响的警报，直到解除。Telegram 在拉响时发一条 ⚠️，解除时发一条 ✅。
- 鉴权失败（401、403、invalid_grant）和 feed 自己报的 `problem` 第一次就响。其余的连着失败到 `config.json` 的 `health` 阈值才响，免得一次偶发的重试就吵人。下一次成功就解除。
- 警报只在内存里。宿主重启后，还没修好的会在下一次失败时再响、再发一条。
- 模块关掉时，它的 feed 的警报悄悄撤下，不发 ✅：它没有修好，只是不看了。

ADR-0020 里 `problem` 写「通知」宿主行的做法由此取代：`problem` 现在是这个 feed 的警报，文字照旧由模块代码写死。

## 没有采用的做法

- **警报写成对话里的宿主行。** 对话会被重复的行填满，问题还没修好行就被冲走，站着的问题没有一个固定的地方看。
- **警报存进 `state.db`。** 重启后几分钟内每个模型和 feed 都会再试一次，存下的警报反而可能比原因活得久。
- **把模块工具（比如 stock-ta 的 `quote`）现查失败也算进警报。** 使用者自己问的，失败就写在回答里。报价 feed 在交易时段每分钟都在取同一家，断了会从 feed 那里响。工具成功时还得替 feed 解除警报，两件事会混在一起。
