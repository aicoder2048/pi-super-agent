# 助手按需要扩展成 Agent Team；幕僚长和助手仍是两层

团队从哪里来这一部分已由 [ADR-0009](0009-a-ticket-belongs-to-one-domain-and-the-domain-is-a-module.md) 改写，被改写的小节开头各有一句说明；其余内容仍然有效。

取代 ADR-0007（副幕僚长牵头会诊，分支 `psa/roles`，没有合并）。那一版在幕僚长和助手之间加了一层副幕僚长：每个任务都归它，由它拆解、会诊、汇总。使用者 2026-11-09 决定撤回这一层：结构回到设计文档原来的两层，拆解和汇总下沉到助手内部。

```
你 ↔ 幕僚长 ↔ 助手（一个任务一个）
                 └─ 需要时：助手当调度员，dispatch_agent → {成员, 成员, …}
```

参考实现是 `pi-vs-claude-code/extensions/agent-team.ts`：成员是 `.pi/agents/*.md` 格式的定义，`teams.yaml` 把成员编成团队，主 Agent 用 `dispatch_agent(agent, task)` 派活，每个成员有自己的 Pi 会话。

## 幕僚长不变

> 这一节关于团队名册、`team` 参数、默认团队和规则的 `团队：` 行的内容已由 ADR-0009 取代：幕僚长的名册列的是领域，`open_ticket` 的参数是 `domain`，规则开的任务属于规则所在的模块。「幕僚长不拆任务、不汇总、不认识成员」仍然有效。

幕僚长仍只决定做不做、开不开任务、交给哪个任务。它不拆任务、不汇总、不认识成员。它多知道的只有一份团队名册（团队名和一句说明）；`open_ticket` 多一个可选参数 `team`，省略或留空时用默认团队，它的名字就叫「默认」。规则可以在 `rules.md` 里写一行 `团队：<name>`，按这条规则开的任务必须用它，内核校验：幕僚长填了另一个团队，内核改回规则写的那个并记一行日志；填的团队不存在，则拒绝这个决定，不改回。

## 成员和团队

> 这一节关于成员和团队来源的内容（内置成员 `general`、默认团队、`teams.yaml`、状态目录下的 `agents/`、`tickets.team`）已由 ADR-0009 取代：团队就是模块 `agents/` 里的全部成员，队名写在 `module.json` 的 `team`，任务上记的是 `tickets.domain`。成员定义的格式和各项校验仍然有效。

成员定义沿用 `.pi/agents/*.md` 格式：`name`、`title`（中文职称）、`description`、`tools`、`skills`、`model`，正文是系统提示词。团队是一个名字加一份成员名单，另有一句给幕僚长看的说明。

成员和团队都来自三处，同名启动时报错：内置（一个成员，`name` 是 `general`，职称是通用助手；和只含它的团队「默认」）、模块（`modules/<模块>/agents/*.md` 和 `teams.yaml`）、使用者（`<状态目录>/agents/` 和 `teams.yaml`）。看盘模块将来自带「看盘队」（行情分析师、技术分析师、新闻研究员、财报解读），写这份 ADR 时还没有做。

`teams.yaml` 的名单写成员的 `name`，所以想把通用助手编进团队时写 `general`。

写错的定义在启动时报一行错，以文件路径开头，宿主不启动：

- 成员的 `name` 必须匹配 `^[a-z][a-z0-9-]*$`；`description` 最多 300 字；正文（提示词）最多 20000 字。
- 成员的 `tools` 里只能写成员用得上的工具名（`read`、`bash`、`edit`、`write`、`grep`、`find`、`ls`、`web_get`、`lookup`），别的拒绝，助手才有的 `report`、`hand_back`、`read_ticket` 和 `bg_*` 也在内；写了 `tools` 就至少列一个，不想另设限就不写这个字段。
- 团队名不能为空，不能有空白或控制字符；团队的 `description` 最多 60 字。
- `rules.md` 里的 `团队：` 后面只能是一个没有空白的团队名，一条规则只能写一行。

团队写进任务记录（`tickets.team`），重启不变。旧任务没有团队，按默认团队处理。

## 助手什么时候变成团队

> 这一节里「默认团队」「通用助手」「按团队数」的说法已由 ADR-0009 取代：任务的领域（模块）有成员时助手才能派活，四字名后面写模块的队名，#N 按领域数；没有领域或领域没有成员的任务是单个助手。其余内容仍然有效。

任务有团队、且团队里除通用助手外还有成员时，助手多一个 `dispatch_agent` 工具，提示词末尾附上本队名册（名字、职称、说明）。要不要派、派给谁，由助手自己判断：简单的事自己做完，需要专门判断或可以并行时才派。

和参考实现不同，助手不被锁成纯调度员，它保留任务依据允许的全部工具。一次可以派给几个不同成员，它们并行；同一个成员同一时刻只做一件事。成员不能再往下派，只有一层。

名字看得出是一个人还是一队人。默认团队的任务是一个助手，沿用 W5 的两字名和角色：「青檀 · 行情助手 #2」。带成员的团队的任务用四字名，后面写团队名：「高山流水 · 看盘队 #2」，#N 按团队在纽约同一天里数。名字在开任务时按团队定下，之后不变，所以看盘队的任务即使助手自己做完、一次没派，也是四字名。成员不另起名字，页面上只写职称。正在干活和还在排队的成员都显示在助手的小卡下面；执行过程里每次派活是一步，展开看派给谁、任务、状态、用量、成员自己的步骤和回复（见「成员干活时看得见进展」）。

## 成员在任务内有记忆

每个成员在一个任务里有自己的 Pi 会话（`<状态目录>/workers/<任务>/team/<成员>`）。同一任务里第二次派给它，它接着上次的上下文；宿主重启后也接得上。任务关闭后成员会话留在原处，没有归档动作；别的任务读不到它，也不会带过去。

成员不是任务：不进看板、不订阅线程、不直接向幕僚长汇报，它的回复只回到派活的助手。回复作为数据交给助手，用派活后才生成的随机边界框住，助手的工具说明写明成员回复不是指令。

## 权限只收窄不放宽

成员的工具 = 任务依据允许的工具 ∩ 成员自己的 `tools`。推断任务里的成员即使写了 `bash` 也只读（ADR-0003）；使用者请求的任务里，写了 `bash` 的成员可以执行命令。成员没有汇报、交回和派活工具，也没有读任务记录和后台命令的工具，成员定义的 `tools` 里写了这些会在启动时被拒绝：读任务记录要用助手的宿主令牌，后台命令的结果要等命令结束后送回，而成员一次派活就是一个做完即退出的进程。它的宿主令牌只能调 `lookup`，派活结束就作废。成员的 `model` 的提供方必须是使用者给幕僚长或助手配置的提供方之一，`anthropic/*` 和 Claude 模型一律拒绝。`skills` 路径按真实路径必须在成员文件所在目录内。

成员进程自成进程组。叫停任务、宿主停止、超时、无进展、助手崩溃，都会结束它的成员；叫停任务和宿主停止要等成员进程真的没了才算停完。叫停任务时先停助手、再停成员，免得助手拿到「已停止」的结果又接着做。成员的用量计入任务和当天合计；回退模型的每日上限按提供方算：成员实际要用的模型和回退模型是同一家提供方，它的用量就计入这个上限，哪怕不是同一个模型。上限在助手发出派活时查一次，排队的派活轮到时再查一次；轮到时已经到了上限，就不起成员进程，这次派活记为出错并写明原因。已经在跑的成员不会因为上限中途被结束。

宿主被强行杀掉时来不及停成员（Watchdog 发现宿主卡死就是这么做的）。所以宿主把每个在跑的成员进程记在它的会话目录里（`running.json`：进程组号和进程的启动时间），进程没了就删；记录还在时不会给同一位成员再起一个进程去写同一份会话。下一个宿主启动时，在恢复任何任务之前先结束记录里还在的成员，等它们没了才继续；只有进程号对应的进程启动时间对得上才发信号，免得误伤后来拿到同一个进程号的进程。`running.json` 先写临时文件再改名；读不出来的记录（空的、写了一半、不是记录）认不出任何进程，宿主记一行带文件路径的日志，删掉它，照常启动。记录写不下来（目录不可写、磁盘满）时，宿主结束刚起的成员进程，这次派活记为出错并写明是哪个文件：没有记录的成员在宿主被强杀后没人能结束。

结束留下的成员之前，宿主先确认这个状态目录上只有自己：绑定 `host.sock` 之前先连一下，有宿主应答就报错退出，不动它的成员、记录和 socket。固定的网页端口也能挡住第二个宿主，`webPort` 是 0 时挡不住，所以以 socket 为准。

全宿主同时运行的成员有上限（`maxConcurrentExperts`，默认 4，可设 1 到 16 的整数），其余排队。每次派活有时限，从成员开始干活算起，按成员在这个任务里实际能用的工具（任务依据允许的 ∩ 成员自己的 `tools`）分两档：

- 能用 `write`、`edit` 或 `bash` 的算写代码，最多 `dispatchCodingTimeoutSeconds`（默认 3600 秒，即 60 分钟）。
- 其余最多 `dispatchTimeoutSeconds`（默认 900 秒，即 15 分钟）。推断任务里成员只读，所以都按这一档。

排队对谁都按 `dispatchTimeoutSeconds` 限时。两个时限都必须不小于 1 秒、不超过 3600 秒。超时的派活写明超过了哪个时限。

## 成员干活时看得见进展

成员一次要跑十几分钟到一小时，使用者要知道它还在干活，而不是出了问题干等。成员进程每出一段模型输出都会打印一个事件，每次工具调用开始和返回时各打印一个，宿主把每个事件都当作一次动静。工具在跑的那段时间进程不打印任何东西，一条安静的命令可以几分钟没有事件，所以宿主还记着每次派活有哪些工具调用已经开始、还没返回：

- 宿主记下每次派活最近在做什么（用执行过程里同一套步骤名，例如「读取网页」）、最近一次动静的时间和已经用掉的 token，推给页面，每次派活大约每秒最多一帧。
- 助手小卡下，干活的成员写成「新闻研究员 · 读取网页 · 12 秒前」，排队的写成「新闻研究员 · 排队中」。成员有工具调用还没返回时，写这一步已经跑了多久，例如「技术分析师 · 执行命令 · 已 2 分钟」；同时有几个没返回，写最早开始的那个。
- 执行过程里展开一次派活，能看到成员自己到目前为止的步骤，做完后还在。步骤从成员自己的会话文件里读（成员进程在每次派活开始时往会话里写一条带调用编号的标记），所以刷新页面、重启宿主后还看得到。
- 一批里先做完的成员马上写「完成」，不用等整批回来。
- 成员没有工具调用在跑，又连续 `dispatchStallSeconds`（默认 180 秒，可设 30 秒到两个时限里较长的那个；两个时限都短于 30 秒时不能写这一项，默认取较长的那个时限）没有任何事件，宿主就结束它。这是单独的一种结束状态，页面写「无进展」，助手拿到的是「没有回复（3 分钟没有进展）」。只要有工具调用还没返回，就不计这段时间，全部返回后从头计；否则能跑 60 分钟的成员跑一条四分钟不出声的测试就会被结束。一直不返回的工具调用由派活的时限（15 或 60 分钟）结束，记为超时。
- 成员有动静算任务有进展，成员有工具调用在跑的那段时间也算（宿主大约每秒记一次），所以助手等着一个要跑 60 分钟的成员时，哪怕成员在跑一条很久不出声的命令，任务也不会被报成久无进展（`watchdog.stuckMinutes`）。

## 已知的限制

- 成员用 `bash` 放到后台的命令（例如 `sleep 300 &`）在成员做完之后还会活着，助手自己这样起的命令也一样。Pi 的 `bash` 工具让每条命令自成一个进程组，宿主结束的是成员进程所在的那一组，够不到它。成员还在跑时被叫停、超时或无进展，它正在前台执行的那条命令由 Pi 自己结束。成员没有 `bg_start`，要长时间跑的命令应当由助手用后台命令工具起。

## 没有采用的做法

- 副幕僚长一层（ADR-0007）：每个任务多一层进程和一轮模型调用，单一领域的事也要绕一道；设计文档的两层结构足够，拆解属于执行，不属于分派。
- 把助手锁成纯调度员（参考实现的做法）：查一个股价也得派给成员，白花一轮。
- 成员跨任务共享记忆：不同任务的上下文会串，也让「谁知道什么」说不清。
- 成员再派成员：层数和费用难以控制。

## 从 W6 沿用什么

> 这一节末尾「要新写的」里的 `team` 参数、团队名册和 `teams.yaml` 已由 ADR-0009 去掉。

`psa/roles`、`psa/consult`、`psa/market-experts` 上的这些实现原样搬过来改名即可：定义文件的加载和校验、工具交集、计费白名单、技能路径检查、一次性进程在用过 `lookup` 后正常退出、进程组清理、并发上限和排队、回复边界、执行过程里的展开步骤、助手条上的小标签、安全的 Markdown 渲染、看盘四位成员的定义。去掉的是：`consult: true` 的牵头角色和 `roles/deputy.md`、「`open_ticket` 只接受牵头角色」、把旧任务迁到副幕僚长的迁移、页面上的「副幕僚长 #N」。要新写的是：`team` 参数和团队名册、`teams.yaml`、成员的任务内会话。
