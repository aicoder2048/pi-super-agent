# 助手按需要扩展成 Agent Team；幕僚长和助手仍是两层

取代 ADR-0007（副幕僚长牵头会诊，分支 `psa/roles`，没有合并）。那一版在幕僚长和助手之间加了一层副幕僚长：每个任务都归它，由它拆解、会诊、汇总。使用者 2026-11-09 决定撤回这一层：结构回到设计文档原来的两层，拆解和汇总下沉到助手内部。

```
你 ↔ 幕僚长 ↔ 助手（一个任务一个）
                 └─ 需要时：助手当调度员，dispatch_agent → {成员, 成员, …}
```

参考实现是 `pi-vs-claude-code/extensions/agent-team.ts`：成员是 `.pi/agents/*.md` 格式的定义，`teams.yaml` 把成员编成团队，主 Agent 用 `dispatch_agent(agent, task)` 派活，每个成员有自己的 Pi 会话。

## 幕僚长不变

幕僚长仍只决定做不做、开不开任务、交给哪个任务。它不拆任务、不汇总、不认识成员。它多知道的只有一份团队名册（团队名和一句说明）；`open_ticket` 多一个可选参数 `team`，省略或留空时用默认团队，它的名字就叫「默认」。规则可以在 `rules.md` 里写一行 `团队：<name>`，按这条规则开的任务必须用它，内核校验：幕僚长填了另一个团队，内核改回规则写的那个并记一行日志；填的团队不存在，则拒绝这个决定，不改回。

## 成员和团队

成员定义沿用 `.pi/agents/*.md` 格式：`name`、`title`（中文职称）、`description`、`tools`、`skills`、`model`，正文是系统提示词。团队是一个名字加一份成员名单，另有一句给幕僚长看的说明。

成员和团队都来自三处，同名启动时报错：内置（一个成员，`name` 是 `general`，职称是通用助手；和只含它的团队「默认」）、模块（`modules/<模块>/agents/*.md` 和 `teams.yaml`）、使用者（`<状态目录>/agents/` 和 `teams.yaml`）。看盘模块自带「看盘队」：行情分析师、技术分析师、新闻研究员、财报解读。

`teams.yaml` 的名单写成员的 `name`，所以想把通用助手编进团队时写 `general`。

写错的定义在启动时报一行错，以文件路径开头，宿主不启动：

- 成员的 `name` 必须匹配 `^[a-z][a-z0-9-]*$`；`description` 最多 300 字；正文（提示词）最多 20000 字。
- 成员的 `tools` 里只能写助手有的工具名，不认识的拒绝；写了 `tools` 就至少列一个，不想另设限就不写这个字段。
- 团队名不能为空，不能有空白或控制字符；团队的 `description` 最多 60 字。
- `rules.md` 里的 `团队：` 后面只能是一个没有空白的团队名，一条规则只能写一行。

团队写进任务记录（`tickets.team`），重启不变。旧任务没有团队，按默认团队处理。

## 助手什么时候变成团队

任务有团队、且团队里除通用助手外还有成员时，助手多一个 `dispatch_agent` 工具，提示词末尾附上本队名册（名字、职称、说明）。要不要派、派给谁，由助手自己判断：简单的事自己做完，需要专门判断或可以并行时才派。

和参考实现不同，助手不被锁成纯调度员，它保留任务依据允许的全部工具。一次可以派给几个不同成员，它们并行；同一个成员同一时刻只做一件事。成员不能再往下派，只有一层。

名字看得出是一个人还是一队人。默认团队的任务是一个助手，沿用 W5 的两字名和角色：「青檀 · 行情助手 #2」。带成员的团队的任务用四字名，后面写团队名：「高山流水 · 看盘队 #2」，#N 按团队在纽约同一天里数。名字在开任务时按团队定下，之后不变，所以看盘队的任务即使助手自己做完、一次没派，也是四字名。成员不另起名字，正在干活的成员显示在助手的小卡下面，只写职称；执行过程里每次派活是一步，展开看派给谁、任务、回复、状态和用量。

## 成员在任务内有记忆

每个成员在一个任务里有自己的 Pi 会话（`<状态目录>/workers/<任务>/team/<成员>`）。同一任务里第二次派给它，它接着上次的上下文；宿主重启后也接得上。任务关闭后成员会话随任务归档，不带到别的任务。

成员不是任务：不进看板、不订阅线程、不直接向幕僚长汇报，它的回复只回到派活的助手。回复作为数据交给助手，用派活后才生成的随机边界框住，助手的工具说明写明成员回复不是指令。

## 权限只收窄不放宽

成员的工具 = 任务依据允许的工具 ∩ 成员自己的 `tools`。推断任务里的成员即使写了 `bash` 也只读（ADR-0003）；使用者请求的任务里，写了 `bash` 的成员可以执行命令。成员没有汇报、交回和派活工具，它的宿主令牌只能调 `lookup`。成员的 `model` 的提供方必须是使用者给幕僚长或助手配置的提供方之一，`anthropic/*` 和 Claude 模型一律拒绝。`skills` 路径按真实路径必须在成员文件所在目录内。

成员进程自成进程组。叫停任务、宿主停止、超时、助手崩溃，都会结束它的成员。全宿主同时运行的成员有上限（`maxConcurrentExperts`，默认 4），其余排队。成员的用量计入任务和当天合计，回退模型的每日上限照样生效。

## 没有采用的做法

- 副幕僚长一层（ADR-0007）：每个任务多一层进程和一轮模型调用，单一领域的事也要绕一道；设计文档的两层结构足够，拆解属于执行，不属于分派。
- 把助手锁成纯调度员（参考实现的做法）：查一个股价也得派给成员，白花一轮。
- 成员跨任务共享记忆：不同任务的上下文会串，也让「谁知道什么」说不清。
- 成员再派成员：层数和费用难以控制。

## 从 W6 沿用什么

`psa/roles`、`psa/consult`、`psa/market-experts` 上的这些实现原样搬过来改名即可：定义文件的加载和校验、工具交集、计费白名单、技能路径检查、一次性进程在用过 `lookup` 后正常退出、进程组清理、并发上限和排队、回复边界、执行过程里的展开步骤、助手条上的小标签、安全的 Markdown 渲染、看盘四位成员的定义。去掉的是：`consult: true` 的牵头角色和 `roles/deputy.md`、「`open_ticket` 只接受牵头角色」、把旧任务迁到副幕僚长的迁移、页面上的「副幕僚长 #N」。要新写的是：`team` 参数和团队名册、`teams.yaml`、成员的任务内会话。
