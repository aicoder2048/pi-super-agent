# 一个任务属于一个领域，领域就是模块

改写 ADR-0008 里「成员和团队」「幕僚长不变」两节关于团队来源的部分；ADR-0008 其余内容（助手按需派活、成员在任务内有记忆、权限只收窄、时限和进展）不变。使用者 2026-11-09 决定。

## 问题

T1 做完后，「领域」有两个互不相通的落点：

- 模块（MVP 就有）：一个文件夹装来源、规则、技能。任务只有被这个模块的规则触发时，助手才拿到它的技能。
- 团队（T1 加的）：`teams.yaml` 把成员编成队，幕僚长开任务时填 `team`，规则用 `团队：` 钉住。

同一个任务身上有两条线索指向领域，各管一半知识。对话里问「NVDA 今天为什么跌」开出的任务归了看盘队，却拿不到看盘模块的技能；规则要绕三步（来源 → 规则 → 团队）才找到人手；同一条经验要在技能和成员提示词里各写一遍。

## 决定

任务上只记一个**领域**，领域就是模块。其余都从它推出来。

```
modules/us-market/
├── module.json   清单：name、title（领域名）、description（给幕僚长的一句话）、team（队名）、sources、timers
├── rules.md      事件驱动面：这类事件怎么处理
├── skills/       人手面：领域经验，助手和成员共用
└── agents/       人手面：专家成员的定义
```

一个模块同时服务两面，连接点只有任务上的领域：

| | 事件驱动面 | 人手面 |
|---|---|---|
| 谁读 | 宿主和幕僚长 | 助手和成员 |
| 读什么 | `sources`、`timers`、`rules.md`、`description` | `skills/`、`agents/` |
| 什么时候 | 事件进来时；幕僚长决定任务归哪个领域时 | 助手启动时；它派活给成员时 |

具体规则：

- **幕僚长的名册列领域。** 每个写了 `description` 的模块一行：名字、领域名、说明。`open_ticket` 的可选参数是 `domain`，填模块的 `name`；省略就是不属于任何领域，由一个通用助手处理。幕僚长只能选名册上的领域：不存在的领域、没写 `description` 所以不在名册上的模块，都拒绝该决定并说明，说明里只列名册上的领域。
- **规则的任务属于规则所在的模块。** 模块 `rules.md` 里的规则开出的任务，领域就是这个模块，由内核按规则编号定，幕僚长填什么都不改变它。规则里不再写 `团队：`，写了启动报错并说明改法。使用者自己的规则（状态目录的 `rules.md`）不属于任何模块，领域由幕僚长选。
- **团队就是模块 `agents/` 里的全部成员。** 没有 `teams.yaml`。模块里有成员，这个领域的助手就能派活，`module.json` 必须写 `team`（队名，如「看盘队」）；没有成员就是单个助手。一个模块最多一支队伍，一位成员只属于它所在的模块。
- **知识跟着领域走。** 任务属于哪个领域，助手就拿到那个模块的 `skills/`，不管任务是规则触发的还是对话里开的。成员拿到同一份 `skills/`，再加自己定义里的 `skills`。模块的 `prepare`（助手第一次启动前在任务工作目录里跑一次的 shell 命令）也跟着领域走，只有一个例外：推断开的任务不跑 `prepare`。推断开的任务只读（ADR-0003），宿主不替它执行任何命令；它的助手照样拿到模块的 `skills/`。
- **提示词和技能分工。** 技能放可复用的经验和资料。成员的提示词只写角色、判断标准和汇报格式，不重复技能里的内容。
- **使用者自己的领域也是模块。** 放在 `<状态目录>/modules/<名字>/`。状态目录下零散的 `agents/` 和 `teams.yaml` 不再读取，存在时启动报错并说明搬到哪里。
- **成员定义提前就绪，进程按需启动。** 宿主启动时读入并校验所有模块的成员（工具、技能路径、模型的计费检查、同一模块内的同名冲突）。成员进程仍在派活那一刻才启动，任务内续接自己的会话。不预先启动成员进程：实测启动到开始干活不到 1 秒，常驻进程空闲时也占名额，重启后仍要靠会话文件恢复。
- **显示。** 领域有成员的任务用四字名加队名：「高山流水 · 看盘队 #2」，#N 按领域在纽约同一天里数。其余任务用两字名加角色，和 W5 一样。
- **存储。** `tickets.domain` 记模块名，空值表示没有领域。T1 的 `tickets.team` 列不再读写；T1 没有合并到 main，不做数据迁移。领域的模块后来被拿掉时，任务按没有领域的单个助手继续，记一行日志。模块没有单独的开关：拿掉一个模块只有两种办法，删掉它的文件夹，或让它所在的目录不再列在 `config.json` 的 `modulesDirs` 里。

## 实现时补充（D1）

写代码时定下的细节。第一条改了上面「成员定义提前就绪」一条的原话，其余是补充。

- 成员重名只在一个模块内查，不同模块可以有同名成员。原话写的是「同名冲突」，没说范围；成员只属于它所在的模块，成员的会话和名额都按任务算，一个任务只有一个领域，跨模块同名不会撞。
- 写了 `description` 就必须写 `title`，`description` 最多 60 字。名册的一行是「- 名字（领域名）：说明」。
- 模块不能叫 `user`。这个名字是使用者规则的编号前缀，叫 `user` 的模块会把使用者自己的规则收进它的领域。
- 幕僚长给模块规则的任务填了别的领域时，内核按规则所在的模块开任务并记一行日志；填的领域不存在时照样拒绝，和别的任务一样。
- 四字名还是两字名、名字和 #N 在开任务时定下，之后不变。队名不存在任务上，读任务时取模块现在写的 `team`：模块改了队名，旧任务跟着变；模块没了成员或被拿掉，队名的位置写模块的 `name`（例如「高山流水 · us-market #2」）。T1 开的团队任务没有领域，这个位置写「团队」。
- 成员每次派活时拿到的技能是模块的 `skills/` 在前，自己定义里的 `skills` 在后。成员自己的 `skills` 路径仍然必须在成员文件所在目录内。
- 加载模块的调用方没有交代可用的提供方时，写了 `model` 的成员一律被拒，不会放行。宿主和 `just market-smoke` 都交代 router 和 worker 的提供方。

## 复查后补充（D1 修订）

独立复查之后定下的。第一条是使用者的决定，其余是补上的校验。

- 推断开的任务不跑模块的 `prepare`，见上面「知识跟着领域走」。任务的 basis 开任务时定下、之后不变，所以同一个任务不会先不跑后来又跑。
- `open_ticket` 的 `domain` 填 `null` 算省略，两头的空白去掉再认，大小写不同不算同一个领域。
- 模块规则的任务，幕僚长填的正好是规则所在的模块时照开，即使这个模块不在名册上：领域是内核按规则定的，幕僚长没有选。
- `module.json` 的 `name`、`title`、`description` 里不能有换行和别的控制字符。`title` 和 `description` 会原样写进幕僚长的提示词，带换行的领域名能在那里伪造出一个标题。
- 模块目录里放错位置的文件启动报错，不再悄悄跳过：直接放在模块目录下的 `teams.yaml`、直接放在模块目录下的 `agents/`（里面有成员文件）、有 `agents/`、`teams.yaml`、`rules.md` 或 `skills/` 却没有 `module.json` 的文件夹。这四样都没有的文件夹照旧不管。
- 模块重名、成员重名、`module.json` 不是一个 JSON 对象，各报一行，以要先打开的那个文件或文件夹的路径开头。

## 去掉的东西

`teams.yaml` 及其解析、规则的 `团队：` 行、`open_ticket` 的 `team` 参数、内置成员 `general` 和名叫「默认」的默认团队、状态目录下零散的成员和团队文件、「技能只给规则触发的任务」这条接线。

## 没有采用的做法

- 保留 `teams.yaml`，只加「技能按团队送达」：两个落点还在，规则仍要绕三步。
- 一个模块多支队伍、成员跨模块复用（参考实现的做法）：目前没有用例；需要时拆成两个模块。
- 把来源和团队拆成两个模块：规则会变成跨模块引用，拿掉一个另一个就在启动时报错。
- 预先启动成员进程：见上。等有具体场景（例如开盘前预热）再作为单独的决定。

## 以后

模块里的数据（棋谱、案例库）还没有位置，等有具体数据时单独设计。信道（邮件、IM、GitHub）不放进模块：信道涉及「谁算使用者」，是授权问题，由宿主和单独的 ADR 管。
